\chapter*{Abstract}

This report describes a small system on chip built around a multi-cycle RV32I core, written
in Verilog and run at 200~MHz on the Kintex-7 FPGA of a Digilent Genesys~2 board. The core
executes the RV32I base integer instruction set, one instruction at a time, in four to six
clock cycles each, under a seven-state finite state machine. Around it sit 6~KB of block RAM,
a memory-mapped LED register, a UART transmitter and a controller for the board's 32~MB QSPI
flash, all on one bus that the core sees as plain memory. Two boot modes share the same
hardware. In BRAM boot the firmware image is part of the bitstream and the program runs from
the RAM; in flash boot the core executes a program in place from the flash, which admits
programs larger than the RAM at about a hundredth of the speed.

The design follows Bruno Levy's \emph{From Blinker to RISC-V}. It is checked at three
levels: an ALU bench against values worked out by hand, a golden trace of the mandelbrot demo's
UART output and cycle count, and a lint of the repository's conventions; each is a make target
whose log a commit must cite. The whole SoC takes \implLUTs{} look-up tables and \implFFs{}
flip-flops, under half a percent of the device, meets its 5~ns clock period with \implWNS~ns
to spare, and is estimated to draw \implPowerDynamic~mW beyond the device's static power.

On the board, the mandelbrot demo's first frame is byte for byte the golden trace's, which is
in turn what the C source prints when compiled for a PC, and its frame time of 1.03~s matches
the simulated cycle count to 0.2\,\%. The tinyraytracer demo, five times the RAM's size, ran
in flash boot. The report records the pitfalls met on the way, from the board's UART net names
to the flash clock's hand-over after configuration, and ranks the extensions the next student
could take on: pipelining, the M extension, UART receive, interrupts, DDR3 and HDMI. Every
figure that a script can make is regenerated by a make target from the repository, and the
raw board captures are committed as evidence.

\section{The project}

This is an undergraduate project with one aim: to build a processor that runs compiled C on a
real FPGA board, and to understand every layer between the C source and the lit LED. The
result is the system on chip this report describes: a multi-cycle RV32I core, a few kilobytes
of RAM, a handful of memory-mapped IO registers and a flash controller, wired into one top
level, synthesised for the Kintex-7 of a Digilent Genesys~2, and run on that board at the
board's 200~MHz clock. Figure~\ref{fig:board-mandelbrot} is what it does when the bitstream
loads: it draws the Mandelbrot set over the UART, one frame a second.

RISC-V was the natural instruction set. Its base integer set, RV32I, is 40 instructions, small
enough for one student to implement and check instruction by instruction, and the GNU
toolchain compiles plain C for it, so no compiler had to be written or bent. A multi-cycle
core was the natural first design: one instruction at a time, one state of a state machine
per clock cycle, with every memory wait visible as a state, so that the timing of the block
RAM, the register file and the flash is honest in the state diagram rather than hidden in a
pipeline. The Genesys~2 was the board at hand. Its device is two hundred times larger than
the design needs, and the title page shows how much of the board waits for the next project.

The core and the SoC follow Bruno Levy's \emph{learn-fpga} series \emph{From Blinker to
RISC-V}~\cite{levy-learnfpga}, from the multi-cycle core through memory-mapped IO and the GNU
toolchain to execution from SPI flash. That series is the origin of the design's shape, its
state machine and its bus, and of the demos; the port to the Genesys~2, the verification, the
build flow, the board results and this report are the project's own. The report does not
account module by module for where the design diverges from its origin.

\section{What was built}

The hardware is eleven Verilog modules, one per file, in one clock domain (Chapter~\ref{ch:arch}). The core
sees a single bus, a 32-bit address with a read strobe, write data with a byte mask and a
busy input, and \texttt{IOBus} decodes that bus into three regions by one address bit each:
the RAM, the IO registers and the flash. The RAM is 6~KB of block RAM, shared by instruction
fetch and data; the IO registers are the LEDs, the UART's data register and its status word;
the flash controller turns a read in flash space into one SPI transaction and holds the core
busy for its length. The clock enters through the board's differential input, and the reset
is the board's button, synchronous everywhere.

The core (Chapter~\ref{ch:core}) executes RV32I and nothing beyond it: no multiplier, no
interrupts, no control and status registers. Its state machine has seven states, and an
instruction takes four cycles, a store five and a load six, each cycle accounted for by a
memory or register-file read that is answered one cycle after it is asked. The same hardware
boots two ways (Chapter~\ref{ch:flash}). In BRAM boot the firmware image is read into the
block RAM when the bitstream is synthesised, so a program is part of the bitstream. In flash
boot the core's reset vector points into the board's flash, and it fetches each instruction
from there in place, which allows programs far larger than the RAM at a hundredth of the speed.

The firmware (Chapter~\ref{ch:flow}) is six demos in C and assembly, built by the RISC-V GCC
with a start-up file and a linker script for each boot mode, and an ELF-to-hex converter that
writes the firmware image. The repository (Chapter~\ref{ch:repo}) holds the RTL, the firmware,
the simulation, the Vivado scripts, this report and its figure scripts, and a set of make
targets that build and check all of it; the Vivado project is generated, not committed.
Verification (Chapter~\ref{ch:verif}) is an ALU unit bench, a golden trace of the mandelbrot
demo that the regression must reproduce byte for byte and cycle for cycle, and a lint; each is
a gate whose log a commit cites.

\section{Results in brief}
\label{sec:results-brief}

\begin{itemize}[leftmargin=*, itemsep=2pt]
  \item \textbf{Size and speed.} The routed design is \implLUTs{} LUTs, \implFFs{} flip-flops
    and two block RAM tiles, under half a percent of the XC7K325T. The 200~MHz clock is met
    with \implWNS~ns of slack on the worst path, which is the load path: the unregistered
    load-store address through the region decode into the register-file write. Vivado
    estimates \implPowerTotal~mW on the chip, \implPowerStatic~mW of it the device's static
    power (Chapter~\ref{ch:results}).
  \item \textbf{The board, the simulation and the source agree.} The first mandelbrot frame
    the board sent, 11\,014 bytes, is byte for byte the UART output of the golden trace, and
    that is byte for byte what the C program prints when compiled natively. The board's frame
    time, 1031.8~ms, matches the simulation's 206\,292\,808 cycles at 200~MHz, 1031.46~ms,
    within the timestamps' accuracy (Chapter~\ref{ch:board}).
  \item \textbf{Flash boot works.} tinyraytracer, 29~KB of code and constants against 6~KB of
    RAM, rendered its picture from the flash in 127~s, with one press of the reset button
    after each load, which pitfall~\ref{pit:first-fetch} explains. riscv\_logo, sieve and the
    blinker ran in BRAM boot; ST\_NICCC was not run.
  \item \textbf{The demos are bound by the UART.} At 115\,200~baud a byte takes 87~\textmu s,
    and the mandelbrot frame spends about 956 of its 1032~ms sending; the core's own work is
    the rest. A faster core would not show on these demos.
  \item \textbf{Ten pitfalls are recorded}, P1 to P10 in Chapter~\ref{ch:next}, each with its
    symptom, its cause and where the design or the repository now handles it. The costliest
    were outside the core: the board's UART net names, tools run from the wrong directory, a
    signed shift made unsigned by Verilog's rules, the flash clock's hand-over after
    configuration, and a flash write that clears a bit the factory bitstream needs.
\end{itemize}

\section{How to read this report}

Chapters \ref{ch:board-tools} to~\ref{ch:flow} describe the system from the outside in: the
board and the tools, the repository, the architecture, the core, the memory and the IO, the
boot modes, and the path from a C file to the board. Chapters \ref{ch:verif}
to~\ref{ch:board} are the evidence: how the design is checked, what Vivado made of it, and
what the board did. Chapter~\ref{ch:next} is for whoever extends the design, and
Chapter~\ref{ch:concl} concludes. The appendices hold the memory map, the make targets and
the ISA coverage.

A few terms are used in one sense throughout, in the report, the code and the repository's
documents. The \emph{multi-cycle core} is this CPU, as against a single-cycle or a pipelined
one. \emph{BRAM boot} and \emph{flash boot} are the two boot modes. The \emph{firmware image}
is the one program loaded into the RAM at configuration, \texttt{rtl/firmware.hex}. A
\emph{demo} is one of the six programs under \texttt{fw/}. \emph{Memory-mapped IO} is how
the LEDs and the UART are reached, by ordinary loads and stores. The \emph{final report} is
this document. The design notes, \texttt{docs/design/notes.md}, hold the full reasoning behind
each module; the report states each choice and cites the notes' section by its heading, as
\notes{section}. Every figure that a script can make is regenerated by \texttt{make figures}
in \texttt{docs/design/}, and the recipe for each manual one is in the figures' README.

\paragraph{Clock, reset and LEDs.} The oscillator drives a differential pair and nothing
else, so the clock enters through \texttt{IBUFDS}, on a clock-capable pin pair
(Section~\ref{sec:clock}). The reset button grounds \texttt{CPU\_RESET\_N} against a
10~k$\Omega$ pull-up: the line idles high and goes low while the button is held, hence the
active-low reset of the design. Each LED is driven through 330~$\Omega$ to ground, so a~1 in
the LED register lights it.

\paragraph{UART.} The FT232R turns the USB port into a serial line. The board's net names
take the PC's view for TX and RX and the FPGA's for in and out: \texttt{UART\_TX\_IN} is the
PC's transmit line, buffered by IC25D, into the FPGA, and \texttt{UART\_RX\_OUT} is the
FPGA's transmit line into the bridge's RXD. The design only transmits, on
\texttt{uart\_rx\_out}; mixing the two up is pitfall~\ref{pit:uart-pins}
\notes{UART port names and the pin-direction trap}.

\paragraph{QSPI flash.} The flash sits on the FPGA's configuration pins, so the FPGA can
read its bitstream from it at power-on. The design uses it as plain SPI, one bit each way:
\texttt{DQ0} carries the command and address, \texttt{DQ1} the data. Its clock is the
dedicated CCLK pin, reached only through \texttt{STARTUPE2} (Section~\ref{sec:cclk}).

\paragraph{JTAG and the mode jumper.} The second micro-USB port is Digilent's USB-JTAG
circuit; Vivado's hardware manager loads every bitstream of this report through it, and
writes the flash through it (Chapter~\ref{ch:flash}). JTAG works whatever the jumper says.
The jumper, JP5, sets the mode pins read at power-on: Master~SPI, $M[2{:}0]=001$, configures
the FPGA from the flash, which on the owner's board holds Digilent's factory demo at offset~0,
left untouched; JTAG, $101$, waits for a bitstream over JTAG; Slave Serial, $111$, is not used
here~\cite{ug470}.

\section{The bus and the modules}

The core, \texttt{Processor}, sees one bus and nothing else: a 32-bit byte address, a
one-cycle read strobe, 32 bits of read data, 32 bits of write data with a four-bit byte
mask, and a busy input. The bus has no acknowledge. A read requested with
\texttt{mem\_rstrb} is answered on \texttt{mem\_rdata} in the next cycle, unless
\texttt{mem\_rbusy} is high, and a write lands on the edge where \texttt{mem\_wmask} is
non-zero. Every address falls in some region, so no access is refused
\notes{Processor bus has no notion of RAM versus device}.

Everything around the core follows from that contract. \texttt{IOBus} decodes the address
into three regions, forwards the strobe and the mask to the RAM, holds the LED register,
turns a store into the UART's send pulse and a flash read into an SPI transaction, and
multiplexes the read data back. \texttt{Memory} is 6~KB of block RAM with one port, shared
by instruction fetch and by loads and stores: there is no separate instruction memory. Its
read is registered, which is why the core waits a cycle after every read, and its write
lands on the same edge, which is why a store needs no wait
\notes{Read and write timing are not symmetric}. \texttt{UartTx} sends 8N1 at 115\,200~baud
and \texttt{SPIFlash} reads one 32-bit word per transaction, at a sixth of the system
clock. The flash controller is the only block that stalls the core, by holding
\texttt{mem\_rbusy} for the length of a transaction; the RAM and the IO registers always
answer in the next cycle \notes{Only flash reads stall the core; read mux}.
Chapters~\ref{ch:memio} and~\ref{ch:flash} give each module's timing.
Figure~\ref{fig:rtl-soc} is what Vivado makes of \texttt{SOC.v} before synthesis: the same
six instances. \texttt{Clockworks} is among them but contributes no cell to the netlist,
as Section~\ref{sec:clock} explains.

\label{sec:memmap}

firmware carries copies of its values in \texttt{fw/io.h} and the start-up code, and a lint
rule holds every copy equal to the defines (Chapter~\ref{ch:verif}).

A region is chosen by one address bit, not by a comparator: bit~24 selects the flash, bit~22
selects the IO registers when bit~24 is clear, and an address with neither bit set is RAM.
Inside the IO region each register owns one bit as well, bits~2, 3 and~4, so a store to
\texttt{IO\_BASE + 4} lights the LEDs and a store to \texttt{IO\_BASE + 8} sends a byte. The
whole decode is a few bit tests in \texttt{IOBus}, the address masked with a base and
OR-reduced, and a register is as cheap as a region \notes{Address decode: one bit per
region, one-hot IO registers, why bit 24}.

The flash bit is the one that was chosen with care, because it fixes how much of the chip
is reachable: everything below the selector bit is the offset inside the flash. Bit~23 would
leave 8~MB, which does not reach past the 10.9~MB bitstream that sits at the start of the
same chip; bit~24 leaves 24 bits, 16~MB, exactly the three address bytes of the flash's
\texttt{03h} read command. The IO bit only has to lie between the RAM and the flash, and
bit~22 does. The code window at 13~MB, and why, are in Chapter~\ref{ch:flash}.

The decode has three consequences worth knowing before writing firmware. Nothing is
rejected: an address with no region bit selects the RAM, past its 6~KB end as well, and what
such an access does is undefined; in simulation it reads \texttt{x}. Only the UART
status register answers a read; the LED and UART data registers, and any other IO address,
read as zero. And a write to flash space does nothing: the controller only reads. To add a
peripheral, give it the next free bit of the IO word address, bit~5 at byte offset
\texttt{0x20}, decode it in \texttt{IOBus} as the three existing ones are decoded, add it to
the read mux if it answers reads, and add its copy in \texttt{fw/io.h} to the lint rule.

\section{Clock and reset}
\label{sec:clock}

The board's 200~MHz oscillator drives a differential pair, so the clock enters through
\texttt{IBUFDS}, which turns the pair into one signal, and \texttt{BUFG}, which puts it on a
global clock net \notes{Genesys 2 differential clock input}. That net, \texttt{clk}, is the
only clock in the design; its 5~ns period is the one timing constraint, met with 0.219~ns to
spare (Chapter~\ref{ch:results}).

\texttt{Clockworks} derives two signals from the clock and the button. \texttt{clk\_enable}
is a gearbox: with the parameter \texttt{SLOW} set to $n$, it is high for one cycle in
$2^n$, and the core, the bus and the RAM advance only on those cycles, while the UART and
the flash controller run every cycle, so the baud rate and the SPI clock stay right
\notes{Gearbox counter}. With \texttt{SLOW} at 20 the core runs a million times slower and
the LEDs can be watched; the shipped design sets it to~0, \texttt{clk\_enable} is the
constant~1, and the module synthesises to nothing.

\texttt{reset\_n} is the CPU RESET button, active-low on this board, forwarded as it is: no
synchroniser and no debounce. Every reset in the design is synchronous, and three places
have one: the core's \texttt{pc}, \texttt{instr} and FSM state, the LED register, and the
UART's transmitter. The register file, the RAM and the flash controller have none; the
register file because the core fetches an instruction before it reads any register. The
core's and the LED register's resets are not gated by \texttt{clk\_enable}, so a slowed
design still resets on the next edge \notes{Synchronous reset and the clock enable}.
The core's three registers also declare their reset value as their initial value, which is
what configuration loads into the flip-flop on a 7-series part, so the core leaves
configuration already in its reset state and starts without a press of the button
\notes{Power-on state matches the reset state}. The LED register and the UART declare
none and configure to zero: the LEDs dark, and the UART in its idle state, whose first
clock raises the line and \texttt{ready}. In flash boot a press is still needed on the
board, for a reason that lies in the flash controller's start-up, not here
(pitfall~\ref{pit:first-fetch}).

The one subtlety of the reset is where the FSM lands: in \texttt{WAIT\_DATA}, which asserts
no strobe and falls through to \texttt{FETCH\_INSTR} in the first cycle after the button is
released, and not in \texttt{FETCH\_INSTR} itself. Pitfall~\ref{pit:reset-wait-data} gives
the reason \notes{Reset lands in WAIT\_DATA, not FETCH\_INSTR}.

\chapter{The multi-cycle core}
\label{ch:core}

\texttt{Processor} executes RV32I, the base integer instruction set, and nothing beyond it:
no M extension, no interrupts, no control and status registers; \texttt{ECALL} and
\texttt{EBREAK} stop the core (Appendix~\ref{app:isa}). It is a multi-cycle core: one
instruction at a time, several clock cycles each, one FSM state per cycle. \texttt{Control}
is the FSM; \texttt{Decoder}, \texttt{ALU} and \texttt{RegisterFile} are what their names
say; \texttt{Processor} holds \texttt{pc}, the instruction register and the glue between
the other four.

An instruction takes several cycles because the RAM answers a read one cycle after it is
requested, and because the register file's read is synchronous too, so each of those
needs its own state \notes{Why one instruction takes several cycles}.
Figure~\ref{fig:fsm} shows the seven. \texttt{FETCH\_INSTR} drives \texttt{pc} on the bus
with the read strobe; \texttt{WAIT\_INSTR} latches the word the RAM returns;
\texttt{FETCH\_REGS} latches \texttt{rs1} and \texttt{rs2}; \texttt{EXECUTE} loads
\texttt{pc} with its next value and writes \texttt{rd} for every instruction but a load, a
store or a branch. A load goes on to \texttt{LOAD}, which drives the data address with the
strobe, and \texttt{WAIT\_DATA}, which writes the returned word to \texttt{rd}. A store goes
to \texttt{STORE}, which drives the address, the data and the byte mask for one cycle; the
RAM writes on that same edge, so there is no wait after a store \notes{STORE needs no wait
state}. The two waits are the only states that can last longer than a cycle: they hold
while \texttt{mem\_rbusy} is high, which only the flash controller raises
\notes{Instruction fetch stalls on mem\_rbusy}.

\texttt{Control} decodes four one-cycle strobes from the state, \texttt{latch\_instr},
\texttt{read\_regs}, \texttt{update\_pc} and \texttt{write\_rd}, already qualified with
\texttt{clk\_enable} and \texttt{reset\_n}, so each datapath register tests only its
strobe. \texttt{write\_rd} in \texttt{WAIT\_DATA} is gated by \texttt{mem\_rbusy} as well,
or a stalled flash load would write the bus's garbage to \texttt{rd} on every stalled cycle
\notes{Write-back enable gated by mem\_rbusy in WAIT\_DATA}. Table~\ref{tab:cycles} gives
the cost per instruction class.

Two of the four cycles of the commonest class are the fetch. A pipelined core would
overlap the fetch of one instruction with the execution of the last and retire close to one
instruction per cycle: a gain of four to six on code bound by computation. The demos of
Chapter~\ref{ch:board} are bound by the UART, which sets their pace at any clock, so for
them the multi-cycle core costs nothing visible. Pipelining is the first extension in
Chapter~\ref{ch:next}.

\section{The datapath}

\texttt{Decoder} is purely combinational on the instruction register: the ten class flags
from the opcode, disjoint, so at most one is high and exactly one for every instruction the
core implements; the register indices and
the \texttt{funct3} and \texttt{funct7} fields, at fixed positions in every format; and the
five immediates, sign-extended from bit~31. It also settles the two meanings of
\texttt{funct7[5]}: a subtraction only in the register form, since there is no
\texttt{SUBI} and an \texttt{ADDI} whose immediate happens to set bit~30 must still add,
and an arithmetic shift in both forms \notes{ADD versus SUB: funct7[5] alone is not
enough}.

\texttt{RegisterFile} is the 32 integer registers, in LUT RAM: a synchronous read of
\texttt{rs1} and \texttt{rs2} on \texttt{read\_regs}, a synchronous write of \texttt{rd} on
\texttt{write\_rd}, and \texttt{x0} never written and read as zero explicitly
\notes{x0 reads as zero explicitly}. \texttt{ALU} is combinational
(Figure~\ref{fig:rtl-alu}): its second operand is \texttt{rs2} for register instructions and
the I-immediate for everything else, the shift amount is the low five bits of that operand
either way, \texttt{funct3} picks one of the eight operations, and a second case on
\texttt{funct3} computes the six branch conditions on \texttt{rs1} and \texttt{rs2}, with a
default of zero so that no latch is inferred \notes{Branch comparator default arm}. Both
arms of the right shift are signed, or \texttt{SRA} shifts logically
(pitfall~\ref{pit:sra}).

The rest of \texttt{Processor} is the glue between these. A multiplexer chooses the next
\texttt{pc}: the branch target when a branch is taken, the jump target for \texttt{JAL},
\texttt{rs1} plus the immediate with bit~0 cleared for \texttt{JALR}, otherwise
\texttt{pc + 4} \notes{Why jalr\_target is a named wire}. An adder forms the load or store
address from \texttt{rs1} and the I- or S-immediate. The memory moves whole words, so a byte
or halfword load picks its lane by the address's low two bits and sign-extends unless
\texttt{funct3[2]} says not to, and a store broadcasts \texttt{rs2} into every lane it could
land in and lets the byte mask select \notes{Store data is broadcast to every lane; the
mask selects}. The write-back multiplexer gives \texttt{rd} its value: \texttt{pc + 4} for
the jumps, the U-immediate for \texttt{LUI}, \texttt{pc} plus it for \texttt{AUIPC}, the
aligned load data, or the ALU result. The worst timing path of the design runs through
this glue, from the instruction register through the load-store address adder, the region
decode and the load lanes to the register file's write port (Chapter~\ref{ch:results},
pitfall~\ref{pit:worst-path}).

written to the LEDs: four instructions, 19 cycles, every state of Figure~\ref{fig:fsm}.

The load takes cycles 0 to~5. In \texttt{FETCH\_INSTR} the bus address is \texttt{pc},
\texttt{0x278}, with the strobe; in \texttt{WAIT\_INSTR} the RAM answers with the
instruction word, \texttt{0x00812403}, and \texttt{latch\_instr} moves it into
\texttt{instr} on the edge that ends the cycle. From then on the bus address is the
load-store address, \texttt{sp + 8}. \texttt{EXECUTE} advances \texttt{pc} to
\texttt{0x27c}; \texttt{LOAD} asserts the strobe at the data address; \texttt{WAIT\_DATA}
sees the word,~0, and \texttt{write\_rd} writes it to \texttt{s0}. The two \texttt{LUI}s
take four cycles each, cycles 6 to~13, writing \texttt{rd} in \texttt{EXECUTE}. The store,
cycles 14 to~18, writes no register, so \texttt{write\_rd} stays low in its
\texttt{EXECUTE}; in \texttt{STORE} the bus carries the LED register's address,
\texttt{0x400004}, the byte mask \texttt{f} and the data, and the register takes the value
on the edge that ends the window. Each read is answered one cycle after its strobe, and no
cycle is spent on the store: the two facts about the memory that shaped the FSM.

\chapter{Memory and memory-mapped IO}
\label{ch:memio}

The core reaches everything through the bus of Chapter~\ref{ch:arch}, and to the core the
three regions differ only in timing. The RAM and the IO registers answer every read in the
next cycle and take every write on the edge it is presented; the flash answers a read about
380 cycles later, and the core waits. This chapter gives each target's side of the bus, in
the order of the memory map (Table~\ref{tab:memory-map}).

\section{The RAM}

\texttt{Memory} is 1536 words, 6~KB, of block RAM: two of the Kintex-7's 445 block RAM
tiles. Its one port serves instruction fetch, loads and stores alike, so in BRAM boot the
program, its data and its stack share it, the stack growing down from the top. The read
is registered: the word addressed in the cycle of \texttt{ram\_rstrb} appears on
\texttt{ram\_rdata} at the next edge, which is the one cycle every \texttt{WAIT} state of
the FSM spends. A write needs no strobe and no wait: each of the four
\texttt{ram\_wmask} bits writes its byte lane on the edge where it is high, so \texttt{SB}
and \texttt{SH} change one byte or halfword and leave the rest of the word as it was
\notes{Read and write timing are not symmetric} \notes{Per-byte write enables}. \texttt{IOBus}
masks both strobes off outside RAM space, so a store to an IO register never also writes
the RAM word with the same index \notes{RAM strobes masked outside RAM space}.

The RAM's contents at configuration are the firmware image, \texttt{rtl/firmware.hex}, read
with \texttt{\$readmemh} when the bitstream is synthesised, so a BRAM-boot program is part of
the bitstream and a new program is a new bitstream (Chapter~\ref{ch:flash}). The file is
read by bare name, relative to the working directory of the tool
\notes{Bare file name in \$readmemh}, and a missing file leaves the RAM undefined with no
error, as the header of \texttt{rtl/Memory.v} warns: pitfall~\ref{pit:bare-name}.

\section{The LED register and the UART}

The IO registers are three addresses in the IO region, one address bit each, and none of
them is memory: a store to one is an action and a load from one is a question.

\paragraph{LEDs.} A store to \texttt{IO\_BASE + 4} sets the LED register to the low byte of
the store data; \texttt{SW} and \texttt{SB} both work, since lane~0 carries the low byte of
\texttt{rs2} in every store and \texttt{IOBus} ignores the byte mask. The register drives \texttt{LD0} to \texttt{LD7} directly, clears on reset, and
reads as zero \notes{LED register: reset not gated by the clock enable}.

\paragraph{UART data.} A store to \texttt{IO\_BASE + 8} turns into \texttt{uart\_valid}, a
one-cycle pulse, with the low byte as \texttt{uart\_data}. \texttt{UartTx} drops
\texttt{ready} on the same edge and sends the byte as one start bit, eight data bits LSB
first and one stop bit, each 1736 cycles long: 115\,207~baud, 0.006\,\% above 115\,200. A
byte takes 17\,360 cycles, 86.8~\textmu s. The transmitter has no FIFO and ignores
\texttt{valid} while it sends, so a byte stored too early is lost without a trace
\notes{UART send pulse and the status word (bit 9 convention)}.

\paragraph{UART status.} A load from \texttt{IO\_BASE + 0x10} returns a word that is zero
but for bit~9, which is \texttt{!ready}: the transmitter is busy. The word is not stored
anywhere; \texttt{IOBus} computes it from the address and \texttt{ready} in the cycle the
core reads it. It is the only IO address that answers a read. Bit~9 is a convention between
\texttt{IOBus} and the firmware, held equal by the memory-map lint rule.
\texttt{fw/putchar.S} is the whole driver: it stores the byte, then loads the status word
until bit~9 is clear, so the next character never finds the transmitter busy. This wait is
why the demos of Chapter~\ref{ch:board} run at the pace of the UART.

\section{The flash stall}

A read in flash space is the one access the core waits for. In the cycle of the read
strobe, \texttt{IOBus} passes it to \texttt{SPIFlash} with the word address, the low 22 bits
of the word index; the controller drops chip select and raises \texttt{mem\_rbusy} at the
next edge, and holds both for the whole SPI transaction. The FSM's two wait states hold
while \texttt{mem\_rbusy} is high, and \texttt{write\_rd} in \texttt{WAIT\_DATA} is gated by
it, so a stalled load writes nothing until its word has arrived
\notes{Only flash reads stall the core; read mux}.

Figure~\ref{fig:wave-flash} is one such stall, simulated: the third instruction of
flash-boot start-up, fetched from \texttt{0x1D00008}. The transaction is 64 SPI clocks at a
sixth of the system clock, 33.3~MHz: the opcode \texttt{03h}, the 24-bit byte address
\texttt{0xD00008}, both on \texttt{spiflash\_mosi}, then 32 data bits on
\texttt{spiflash\_miso}. That is 382 cycles of \texttt{mem\_rbusy}, and the instruction takes 386
cycles, 1.93~\textmu s, where one fetched from the RAM takes 4. The word arrives lowest address
first, each byte MSB first, as \texttt{13 01 01 80}; the controller swaps the bytes into
\texttt{0x80010113}, \texttt{addi sp,sp,-2048}, little-endian as the RAM returns it
\notes{Byte order of the received word}. Chip select rises right after the last bit, and
\texttt{mem\_rbusy} with it; in that cycle \texttt{WAIT\_INSTR} sees the word and latches
it, and the core moves on as after any fetch. The controller's clock is held low while chip
select is high, as SPI mode~0 needs, and its divider is held too, so the first clock pulse
of a transaction is as long as the others \notes{Divider held in reset while idle (short first pulse)}
\notes{CLK forced low while idle}.

There is no cache and no prefetch: every word read from the flash is a transaction of its
own, an instruction fetch as much as a load. Code that runs from the flash therefore runs
about a hundred times slower than from the RAM, which is what shapes flash boot in the next
chapter.

\chapter{Boot modes and the SPI flash}
\label{ch:flash}

The core starts at its reset vector, the \texttt{SOC} parameter \texttt{BOOT\_ADDR}, and
that one parameter is the boot mode. At \texttt{BOOT\_ADDR\_BRAM}, address~0, the core runs
the firmware image held in the RAM; at \texttt{BOOT\_ADDR\_FLASH}, \texttt{0x01D0\_0000},
it runs a program stored in the board's flash, in place. The hardware is otherwise the same
\notes{Why the reset vector is a parameter, and why a jump at address 0 is not enough}.

Every boundary is forced. An uncompressed 7-series bitstream holds every configuration
frame whatever the design, so it is 11\,443\,728 bytes, \texttt{0xAE9E10}, for any design on

at 12~MB and the code at 13~MB leave a gap after each. The window ends at 16~MB because
the controller sends the 24-bit address of the plain \texttt{03h} read, which is also why
bit~24 selects flash space (Section~\ref{sec:memmap}); the upper 16~MB of the chip would
need a four-byte address. Flash boot writes only the code window, with
``Configuration File Only'', and never offset~0, and the design is loaded over JTAG: the
board keeps booting the bitstream it booted before, provided the write keeps the flash's
Quad Enable bit (pitfall~\ref{pit:quad-enable}).

\section{CCLK and STARTUPE2}
\label{sec:cclk}

Three of the flash's four pins, chip select and the two data lines, are multi-function
pins of the FPGA: the configuration logic uses them at power-on and releases them to the
design afterwards, so \texttt{spiflash\_csn}, \texttt{spiflash\_mosi} and
\texttt{spiflash\_miso} are ordinary ports in the constraints file. The clock is different.
CCLK is a dedicated configuration pin, and a design can reach it only through the
\texttt{STARTUPE2} primitive~\cite{ug470}: whatever drives its \texttt{USRCCLKO} input
reaches the pin once configuration has ended. \texttt{SOC} wires \texttt{SPIFlash}'s clock
to \texttt{USRCCLKO}, holds \texttt{USRCCLKTS} low so the pin stays driven, and takes
\texttt{EOS}, end of startup, back to \texttt{IOBus}, which passes a flash read to the
controller only once \texttt{EOS} is high \notes{SPI flash CCLK access through STARTUPE2}
\notes{Flash read strobe gated by end-of-startup; 22-bit word address}.

The hand-over is not immediate. Vivado's simulation model of \texttt{STARTUPE2} keeps CCLK
high after end of startup until \texttt{USRCCLKO} has risen twice, so the first transaction
after configuration loses two of its 64 clock edges and the flash misreads its command. In
the simulation behind Figure~\ref{fig:wave-flash} that alone costs the first fetch of
\texttt{fw/start\_spiflash.S}, with the \texttt{EOS} gate playing no part, and it is the most
likely reason flash boot needs one press of the reset button after each load on the board.
Pitfall~\ref{pit:first-fetch} gives the mechanism and a candidate fix.

\section{Execute-in-place}
\label{sec:xip}

In flash boot the code is not copied into the RAM: the core fetches each instruction from
the flash, one transaction per word, and \texttt{.text} and \texttt{.rodata} stay there
\notes{Instruction fetch stalls on mem\_rbusy}. What must be writable cannot stay in the
flash, so \texttt{fw/spiflash.ld} places \texttt{.data} and \texttt{.bss} in the RAM, with
the initial values of \texttt{.data} stored in the flash right after the code, and
\texttt{fw/start\_spiflash.S} prepares the RAM before \texttt{main}: it sets \texttt{gp} to
\texttt{IO\_BASE} and \texttt{sp} to the top of the RAM, zeroes \texttt{.bss}, and copies
the stored values into place, one flash read and one store per word.

The same copy moves the hottest code into the RAM. Every \texttt{*}, \texttt{/} and
\texttt{\%} in C is a call into \texttt{libgcc} on RV32I, and every character goes through
\texttt{putchar} and the print routines, so the linker script puts \texttt{libgcc}'s
multiply and divide, \texttt{fw/putchar.S}, \texttt{fw/print.c} and any function marked
\texttt{.fastcode} in the copied section. The linker gives them RAM addresses, so the code
in the flash calls them there. For mandelbrot's flash build that is 1\,228 bytes copied,
against 1\,172 bytes of code and constants left in the flash. The copy costs time at start-up, six flash
transactions per word, the load and the five instructions of the loop, which are fetched
from the flash too: a few milliseconds for mandelbrot. It also costs RAM for the rest of the
run: what is copied shares the 6~KB with the data and the stack, and nothing checks that the
stack stays clear of it.

\paragraph{From C to machine code.} \texttt{make -C fw} compiles each C file with \texttt{gcc
-c} and links the objects, the start-up code and \texttt{libgcc} with \texttt{ld} into an ELF
\notes{The compiler and linker flags, one by one}. The ELF holds machine code: the store is the
32-bit word \texttt{\flowStoreWord} at address \texttt{\flowStoreAddr}. The assembly in the
figure is \texttt{gcc -S}'s output, written for the reader by \texttt{make -C fw
build/mandelbrot.s}. \texttt{gcc -c} produces the same text as a temporary file and assembles
it within the same command, so the build never keeps it, and nothing after the compiler reads
it: there is no assembler step to look for, and the FPGA never sees an instruction's name. The
assembly shows two things the linked code no longer does. \texttt{li a5,4194304} is a
pseudo-instruction, one \texttt{lui} for \texttt{IO\_BASE}, \texttt{0x400000}; and
\texttt{\%hi(.LC1)} names a string the linker has not placed yet, so the \texttt{lui} reads
\texttt{0x0} only once the string lands below \texttt{0x800}, the first 2~KB.

\paragraph{The firmware image and the block RAMs.} The firmware image is the ELF's bytes as
text for \texttt{Memory.v}'s \texttt{\$readmemh}: \texttt{firmware\_words} writes four words a
line, each most significant digit first, so the store is word~\flowStoreIndex, on
line~\flowStoreHexLine{} \notes{Why the ELF-to-hex conversion exists; endianness}. Synthesis
turns the RAM into two \texttt{\flowBramRef}, each 2K deep and 18 bits wide:
\texttt{\flowBramLow} holds the low 16 bits of every word and \texttt{\flowBramHigh} the high
16, so the store's word is split between them, \texttt{\flowStoreLow} and
\texttt{\flowStoreHigh}, in \texttt{\flowBramInit}, the \texttt{INIT} string of words
\flowBramWords. These \texttt{INIT} values become part of the bitstream, which is why a new
program in BRAM boot needs a new bitstream \notes{Simulation and hardware after a firmware
change}.

\paragraph{The bitstream, JTAG and the board.} \texttt{SOC.bit} begins with a short header, the
design's name, the tool version and the part, and then \flowBitBytes{} bytes of configuration
data, \flowBitFileBytes{} bytes in all, the size of every bitstream for this part
(Figure~\ref{fig:flash-layout}); the FPGA starts reading at the sync word,
\texttt{0xAA995566}~\cite{ug470}. \texttt{board\_program.tcl} loads it over JTAG in
\flowLoadSeconds{}~s, from the script's announcement to Vivado's exit. The first byte of
frame~0 arrives before Vivado has exited: the FPGA runs the design as soon as configuration
ends, while the script still checks DONE. Frame~0 opens with the cursor-home sequence and the
colour of its first pixel, and takes \flowFrameMs{}~ms, which Chapter~\ref{ch:board} compares
with the simulation.

\paragraph{Flash boot.} The same C source, linked with \texttt{fw/spiflash.ld}, runs from the
flash's code window: its first instruction, \texttt{\flowFlashFirst}, sits at
\texttt{0x01D0\_0000}. \texttt{objcopy -O binary} keeps only the bytes, in memory order, so the
word \texttt{\flowFlashWord} becomes \texttt{\flowFlashBytes}, little-endian; the firmware
image writes the same kind of word the other way round, for \texttt{\$readmemh}.
\texttt{write\_cfgmem} wraps the binary in an MCS file, Intel hex for the flash: a record
giving the upper 16 bits of the address, \texttt{\flowMcsUpper}, then 16 data bytes a record.
\texttt{board\_flash.tcl} writes those bytes over JTAG and nothing else, the ``Configuration
File Only'' range; the flash-boot bitstream is loaded as on the left, and the core fetches each
instruction from the flash (Chapter~\ref{ch:flash}). On the board, flash boot ran
tinyraytracer, which does not fit in the RAM (Chapter~\ref{ch:board}); mandelbrot's flash build
is shown as the same program.

\chapter{Verification}
\label{ch:verif}

The design is checked at three levels: one module against values worked out by hand, the whole
SoC against a recorded trace, and the repository against mechanical rules. A make target runs
each check, and each target, a gate, leaves a log that a commit cites.

\section{The ALU unit bench}

\texttt{sim/ALUBench.v} drives the ports of \texttt{rtl/ALU.v} directly and compares ten right
shifts with results worked out by hand from the RV32I specification~\cite{riscv-isa}, not from
the RTL: \texttt{SRL}, \texttt{SRA}, \texttt{SRLI} and \texttt{SRAI} on negative, positive and
most-negative operands, by 0, 4, 9 and~31 places, and with the upper bits of the shift operand
set, which the ALU must ignore. The operand the instruction does not use is set to
\texttt{0xDEADBEEF}, so that a wrong operand choice shows. \texttt{make unit} runs the bench
under iverilog in seconds, and passes only on its final \texttt{PASS} line, so a bench that
stops early fails too.

The bench covers what the golden trace cannot. The golden trace records what the RTL did when
it was captured, right or wrong, so a bug present at capture is part of the reference.
\texttt{SRA} shifted logically when the first trace was captured, and the trace agreed with it
until its frame was compared with the C program compiled natively (pitfall~\ref{pit:sra}). The
bench holds the shifts to the specification, whatever the trace says. It checks the shifts
only; the rest of the ALU is held by the golden trace alone.

\section{The golden trace}

\texttt{sim/bench.v} instantiates \texttt{SOC} in BRAM boot, with \texttt{BOOT\_ADDR} set
to~0, and records only what an observer outside the chip could see: every byte on the UART
line, decoded from the pin as a receiver decodes it, each bit sampled in its middle, and every
change of the LEDs, with its time. It reads no internal signal, so the RTL can be restructured
freely and the same trace still applies. It writes one line per event: a \texttt{UART} line
for each byte, a \texttt{LEDS} line for each change, with its time in nanoseconds, and an
\texttt{END} line that says why and when the run stopped. The golden trace opens with ESC and
closes with its one LED change:

\begin{center}
  \small
  \begin{tabular}{@{}l@{}}
    \texttt{UART 1b} \\
    \quad\vdots \\
    \texttt{LEDS 1031464038 01} \\
    \texttt{END stop\_leds cycles=206292808 uart\_bytes=11014 leds=01} \\
  \end{tabular}
\end{center}

The run stops when the LED register becomes~1, which the mandelbrot demo writes at the top of
its second frame, so the trace holds exactly one frame. The committed trace,
\texttt{sim/golden/mandelbrot\_bram.txt}, is 206\,292\,808 cycles, 1.031~s of simulated time,
with 11\,014 UART bytes and one LED change (\texttt{docs/baseline.md}). Its \texttt{END} line
carries the cycle count on purpose: a change that keeps every byte but alters the timing of a
single instruction fails, so the trace holds the cycle counts of Table~\ref{tab:cycles} as
well as the results.

Two comparisons tie the trace to things outside the simulation. Its UART bytes are, byte for
byte, the first frame \texttt{fw/mandelbrot.c} prints when compiled natively for the PC, so the
trace is what the C source means; and they are, byte for byte, the first frame the real board
sent, whose time matches the cycle count within the board's timestamps' accuracy, about 2~ms
(Chapter~\ref{ch:board}), so the trace is what the hardware does.

\section{The regression}

\texttt{sim/run\_regression.sh} compiles the files of \texttt{vivado/rtl\_sources.txt} and the
bench in xsim, links the committed firmware image into its build directory, since
\texttt{Memory.v} reads it by bare name (pitfall~\ref{pit:bare-name}), simulates, and compares
the new trace with the golden one. It passes only when the two are byte-identical; the full
run takes five to six minutes. With \texttt{--max-cycles} it is the smoke run: the simulation
stops after that many cycles, and the truncated trace must be a prefix of the golden one,
which catches most mistakes in 25~seconds. \texttt{make golden} overwrites the golden trace
with a new run. It is the one way to change the reference, and is meant for an intended change
of behaviour only, whose commit says why and which also redoes \texttt{make baseline}.

The regression runs one program in one boot mode, so it covers what mandelbrot does in BRAM
boot and nothing else. Mandelbrot's code holds 24 of the 37 RV32I instructions other than
\texttt{FENCE}, \texttt{ECALL} and \texttt{EBREAK}; it never executes \texttt{SLL},
\texttt{SRA}, \texttt{SLT}, \texttt{SLTU}, \texttt{XOR}, \texttt{SLTI}, \texttt{SLTIU},
\texttt{XORI}, \texttt{ORI}, \texttt{LB}, \texttt{LH}, \texttt{LHU} or \texttt{SH}, and no
gate runs them through the core; the unit bench checks the ALU's \texttt{SRA} alone. The flash
is not covered either: the bench has no flash model. Flash boot is simulated only by the
report's own bench, \texttt{docs/design/scripts/waves/WaveBench.v}, for the waveforms of
Figure~\ref{fig:wave-flash}, and no gate runs it.

\section{The gates}

The gates are the targets of the root \texttt{Makefile} (Table~\ref{tab:entry-points};
Appendix~\ref{app:make} gives what each runs and needs). Each but \texttt{check}, which only
runs its three parts, writes its output to a log in \texttt{build/logs/}, named after the gate
and the time and ending in \texttt{PASS} or \texttt{FAIL}, and \texttt{docs/CONTRIBUTING.md},
``Gates and evidence'', says which a change needs: \texttt{make lint} before every commit,
\texttt{make smoke} after each RTL edit, \texttt{make -j2 check} once per change, after its
review and before any push, and \texttt{make baseline} as well when the change must show that
timing still holds. A commit
message cites the log of each gate it ran. The commit-msg hook in \texttt{scripts/hooks}
refuses a citation of a log that does not exist or did not pass, and a message that claims a
pass without citing a log; the pre-commit hook runs \texttt{make lint}, and GitHub Actions runs
it again on every push.

\texttt{make check} stops after synthesis and reports no timing; only \texttt{make baseline}
and \texttt{make bitstream} route the design.

\texttt{make lint} holds what no reviewer should have to check by eye. Rule~1 finds tool
by-products beside the sources, which is how a tool run from the wrong directory shows
(pitfall~\ref{pit:bare-name}); rule~2 finds retired paths and vocabulary; rule~3 limits
Markdown prose to 100 characters a line; rule~4 holds \texttt{vivado/rtl\_sources.txt} equal
to the files in \texttt{rtl/}, since a file missing from it would compile nowhere and fail
nowhere; rules 5, 6, 7 and~9 hold the naming and banner conventions of
\texttt{docs/CONTRIBUTING.md}.
Two rules hold copies equal to their source. Rule~8 holds every firmware copy of the memory
map, and the README's tables, equal to \texttt{rtl/defines.vh} (Section~\ref{sec:memmap});
rule~10 holds the trace numbers of \texttt{docs/baseline.md} equal to the golden trace. Each
of the two has a self-test, which changes or deletes every value the rule checks and expects
it to fail, and lint runs both self-tests every time.

The one constraint, the 5~ns period of the 200~MHz clock, is met on every one of the
\implEndpoints{} timed endpoints: the worst setup slack (WNS) is \implWNS~ns and the worst
hold slack \implWHS~ns, so the design would close at up to \implFmax~MHz.

The worst path (Figure~\ref{fig:worst-path-schematic}) starts at \texttt{\implPathStartCell},
an opcode bit of the instruction register, and ends at the data input of the register file's
LUT RAM: the write of \texttt{rd}. It is the load path. Its first \implPathHead{} LUTs decode
the instruction and choose its immediate; a carry chain of \implPathCarry{} \texttt{CARRY4}
adds it to \texttt{rs1}, the load-store address, as far as bit~24, the bit that selects the
flash region \notes{Address decode: one bit per region, one-hot IO registers, why bit 24}; and
the last \implPathTail{} LUTs use that bit to choose the bus's read data, cut out the loaded
byte or halfword and pass it to the write port: \implPathLevels{} levels in all. The address is
not registered. The core computes it from \texttt{instr} and \texttt{rs1} in every cycle of a
load, so the write in \texttt{WAIT\_DATA} waits on the whole adder again. Of the path's
\implPathDelay~ns, \implPathLogic~ns are in the cells and \implPathNet~ns, \implPathNetPct\,\%,
in the routing between them, and a clock skew of \implPathSkew~ns counts against it too.
Routing dominates, as it usually does on an FPGA: fewer levels, not faster cells, would shorten
the path. Registering the load-store address, or only its region bit, would take the adder off
it (pitfall~\ref{pit:worst-path}). Figures~\ref{fig:device-zoom}
and~\ref{fig:worst-path} show it on the device.

tree. The estimate assumes every net toggles at Vivado's default rate; with a simulation's
switching activity it would be more exact, but not different in kind: the core costs a few
milliwatts, and the device costs the rest.

\chapter{Results on the board}
\label{ch:board}

Everything in this chapter was captured from the real board. Each demo's bitstream is loaded
into the FPGA over JTAG and never written to the flash, which keeps Digilent's factory
bitstream at offset~0: the board boots its demo again at the next power-on. Flash boot writes
only the program, at the flash's code offset, over part of the factory demo's data. From the
moment the bitstream starts to load, the host records the UART at 115\,200~baud, 8N1, with a
timestamp on every read, accurate to about 2~ms. The raw captures are committed in
\texttt{docs/design/captures/}, and \texttt{make figures} renders the figures below from them;
\texttt{docs/design/figures/README.md} gives the procedure.

\section{Mandelbrot in BRAM boot}

The mandelbrot demo is the committed firmware image, the one the golden trace was simulated
with. Its bitstream is the synthesised design with \texttt{BOOT\_ADDR} set to
\texttt{BOOT\_ADDR\_BRAM}, as the testbench sets it, so the core starts from the image in the
RAM as soon as configuration ends. Figure~\ref{fig:board-mandelbrot}, which opens this
report, is the first frame the board sent.

\paragraph{The board against the simulation.} The first frame the board sent is 11\,014
bytes long, and it is byte for byte the UART bytes of the golden trace. The golden trace is in
turn byte for byte what \texttt{fw/mandelbrot.c} prints when compiled natively
(\texttt{docs/baseline.md}), so the board, the simulation and the C source agree.

\paragraph{Frame time.} On the board the frame took 1031.8~ms, from its first byte to the
first byte of the next frame. The simulation took 206\,292\,808 cycles from reset to the start
of the next frame, 1031.46~ms at 200~MHz. The start-up code before the first byte is a few
dozen instructions, so the two measure the same interval. They agree to 0.3~ms, within the
timestamps' accuracy of about 2~ms, or 0.2\,\%: to that accuracy, the board takes the cycles
the simulation counts, at 200~MHz. Most
of the frame is the UART. At ten bits per byte, sending the 11\,014 bytes takes about
956~ms, and \texttt{putchar} waits for each byte to leave before it returns, so the
computation itself takes about 75~ms.

\section{tinyraytracer in flash boot}

tinyraytracer is 29\,016 bytes of code and constants, almost five times the 6~KB RAM, so it
runs only in flash boot, executed in place from the flash (Chapter~\ref{ch:flash}). Its flash
image was written to the code window at \texttt{0xD00000} with ``Configuration File Only''. A
readback of the whole 32~MB chip afterwards differed from the one taken before only in the
image's own 29\,016 bytes: the factory bitstream at offset~0 was not touched. Before each
capture, the capture script reads the code window back and compares it with the binary.

\paragraph{The reset button.} With the flash-boot bitstream loaded over JTAG, the core printed
nothing and the LEDs stayed dark: in the capture behind Figure~\ref{fig:board-tinyraytracer},
no byte arrived in the 44~s between the end of the load and a press of the CPU reset button.
From the press on, the demo ran to the end, so flash boot works on this board with the reset
button pressed once after each load (pitfall~\ref{pit:first-fetch}).

\paragraph{The Quad Enable bit.} Writing the image cost the board its power-on boot: the
write cleared the flash's non-volatile Quad Enable bit, which the factory bitstream needs, and
at the next power-on the FPGA stalled in configuration with every byte of the flash intact. A
small design loaded over JTAG set the bit again, a further write of the image with
\texttt{PROGRAM.SKIP\_QE\_BIT\_ERASE} set kept it, and at the next power-on the board booted
Digilent's factory demo again. Pitfall~\ref{pit:quad-enable} gives the cause and the tools.

\paragraph{The picture.} Figure~\ref{fig:board-tinyraytracer} shows what the board sent:
48 by 24 pixels, each one terminal cell, a space on one of xterm's 256 colours.
The run is 21\,412 bytes long and is, byte for byte, what \texttt{fw/tinyraytracer.c} prints
when compiled natively, with \texttt{libm} and floating point in software on the board and in
the host's hardware on the PC. The picture took 126.8~s, 110~ms a pixel: every
floating-point operation is a call into \texttt{libgcc}, and every instruction outside the RAM
is fetched from the flash, one SPI transaction each.

\section{Pitfalls}

Each pitfall below cost time once. Each gives the symptom as it showed, or would show, the
cause, and where the design or the repository now handles it; the other chapters cite them by
number.

\pitfall{pit:uart-pins}{The UART pin-direction trap}
{Not one byte reaches the PC and the bridge's activity LED, LD12, never blinks, while the
design looks healthy inside, in simulation as well.}
{The board's net names mix two points of view: TX and RX are the PC's, \texttt{\_in} and
\texttt{\_out} the FPGA's. \texttt{uart\_rx\_out} is the FPGA's transmit line. Reading
\texttt{\_in} as ``into the PC'' swaps the two pins, and the transmitter drives Y20 against
the bridge's own TXD. A testbench that prints what the core handed the UART, instead of
decoding the pin, cannot see it.}
{The ports of \texttt{SOC} keep their names and directions, which the constraints file and
the testbench bind to (\texttt{docs/CONTRIBUTING.md}), and \texttt{sim/bench.v} decodes the
\texttt{uart\_rx\_out} pin as a receiver does. Chapter~\ref{ch:board-tools} follows the nets
through the schematic \notes{UART port names and the pin-direction trap}.}

\pitfall{pit:bare-name}{The firmware image read by bare file name}
{In simulation the program does nothing: the LEDs stay at zero and the RAM reads
\texttt{x}, with only a warning in xsim's log. After a Vivado run, \texttt{.Xil/} and
\texttt{clockInfo.txt} appear beside the sources.}
{\texttt{Memory.v} reads \texttt{firmware.hex} with \texttt{\$readmemh} by bare name,
relative to the working directory of whichever tool runs, and a missing file leaves the RAM
undefined without an error. A tool started in the wrong directory either finds no image or
leaves its by-products there.}
{Every script that simulates or synthesises runs in a directory of its own with the image
linked or copied in: \texttt{sim/run\_regression.sh} links it into \texttt{sim/build/}, the
root \texttt{Makefile} starts Vivado in \texttt{build/}, and the Vivado project lists the image
in both its filesets. Lint rule~1 fails on by-products beside the sources
(Chapter~\ref{ch:verif}), and the header of \texttt{rtl/Memory.v} warns
\notes{Bare file name in \$readmemh}.}

\pitfall{pit:init-values}{The simulation hang without initial values}
{The simulation runs but the flash controller never starts its clock, and the testbench
hangs; the same RTL works on the board.}
{A register with no initial value starts as \texttt{x} in simulation, and
$\texttt{x} + 1$ stays \texttt{x}: the clock divider of \texttt{SPIFlash} never counted.
Configuration loads a definite value into every flip-flop of the FPGA, so the silicon never
shows the problem.}
{\texttt{div} and \texttt{sclk} in \texttt{rtl/SPIFlash.v} declare initial values
\notes{Explicit initial values on div and sclk (simulation hang)}, and the core's registers
declare their reset values as initial values (Section~\ref{sec:clock}). The register file and
the RAM declare none, hence the \texttt{x} in Figure~\ref{fig:wave-fsm}. A new counter needs
an initial value too.}

\pitfall{pit:sra}{SRA behaving as SRL}
{The golden trace's frame diverged from the C program compiled natively at row~8, pixel~36, and held
8\,368 bytes instead of 11\,014: \texttt{-1544416 >> 9} gave \texttt{0x007FF437} where
\texttt{0xFFFFF437} was right.}
{In Verilog an expression's operands decide its signedness together. In
\texttt{funct7[5] ? (\$signed(a) >>> s) : (a >> s)} the unsigned arm makes the whole
conditional unsigned, and \texttt{>>>} then shifts logically.}
{Both arms of the shift in \texttt{rtl/ALU.v} are signed; \texttt{sim/ALUBench.v} checks
\texttt{SRA}, \texttt{SRAI}, \texttt{SRL} and \texttt{SRLI} on negative operands
(Chapter~\ref{ch:verif}); the golden trace was captured again. The sign fill cost 54 LUTs,
930 to 984 (\texttt{docs/baseline.md}) \notes{SRL versus SRA, as the comment described it}.}

\pitfall{pit:first-fetch}{Flash boot loses its first fetch}
{With the flash-boot bitstream loaded over JTAG, no byte arrives on the UART and the LEDs
stay dark. One press of the CPU RESET button, and the demo runs from then on
(Chapter~\ref{ch:board}).}
{Most likely the core's first fetch from the flash is lost straight after configuration. That
fetch is \texttt{lui gp,0x400}, the first instruction of \texttt{fw/start\_spiflash.S}, which
sets \texttt{gp} to \texttt{IO\_BASE}; without it the UART writes, at \texttt{gp + 8}, land in
RAM address~8, over the code start-up has just copied there. Two parts of the design can lose
it. \texttt{STARTUPE2} passes \texttt{USRCCLKO} to the CCLK pin only after a few edges, so the
first transaction misses clock edges and the flash misreads its command; in simulation this
alone loses the fetch (Section~\ref{sec:cclk}). And \texttt{IOBus} gates
\texttt{spiflash\_rstrb} with \texttt{eos}, so a fetch requested before end of startup is
dropped instead of stalled.}
{On the board only: press the reset button once after each load (the README's ``Flash
boot''). The RTL is unchanged in this report. A candidate fix, not kept in the repository,
made the board print straight after the load: \texttt{eos} moves from \texttt{IOBus} into
\texttt{SPIFlash}, which makes one throwaway read as soon as \texttt{eos} rises, and holds a
read requested before that read is
done, busy, until it can start it. The throwaway read's address is all ones, so a frame that
loses its first clock edges shows the flash only shifted read opcodes, never a write enable,
a program or an erase. An implementation run that was most likely of this fix used about
25 LUTs and 25 flip-flops more than the committed design, and met timing with 0.334~ns of
slack.}

\pitfall{pit:reset-wait-data}{Reset landing in WAIT\_DATA}
{With the reset state changed to \texttt{FETCH\_INSTR}, the obvious choice, nothing shows in
BRAM boot, where the regression runs; in flash boot the first fetch after a press of the reset
button would go wrong.}
{\texttt{FETCH\_INSTR} asserts the read strobe for as long as it lasts. Held in reset there,
with \texttt{pc} in flash space, the core would restart the SPI transaction on every cycle,
chip select held low: the flash would see a command it never finishes, and no deselect to
resynchronise on.}
{\texttt{rtl/Control.v} resets into \texttt{WAIT\_DATA}, which asserts nothing and falls
through to \texttt{FETCH\_INSTR} in the first cycle after reset (Section~\ref{sec:clock}).
Its write-back is harmless, because the instruction register resets to a no-op whose
destination is \texttt{x0} \notes{Reset lands in WAIT\_DATA, not FETCH\_INSTR}.}

\pitfall{pit:worst-path}{The worst path ends in the register-file write}
{A small change on the load path, one more term in the address decode of \texttt{IOBus} or in
the load lanes, can miss the 5~ns of the 200~MHz clock: the worst path has \implWNS~ns of
slack.}
{The load-store address, \texttt{rs1 + imm}, is not registered, so every cycle of a load
computes it again. The path runs from \texttt{instr\_reg[3]}, an opcode bit that picks the
immediate, through \implPathCarry{} \texttt{CARRY4} of the adder to bit~24, the region decode,
the read-data multiplexer and the load lanes, into the register file's write data:
\implPathLevels{} levels and \implPathDelay~ns, \implPathNet~ns of it routing
(Chapter~\ref{ch:results}).}
{Not yet: a comment at \texttt{loadstore\_addr} in \texttt{rtl/Processor.v} marks it. Register
the address in \texttt{EXECUTE}, or only its region bit, and the adder leaves the path.
\texttt{LOAD} and \texttt{STORE} follow \texttt{EXECUTE}, so the register costs no cycle.}

\pitfall{pit:quad-enable}{Writing the flash clears the Quad Enable bit}
{After a flash write with ``Configuration File Only'', the board no longer boots at
power-on: PROG lit, DONE off, the OLED blank, no CRC, ID or bad-packet error, the mode pins
right, and every byte of the flash intact.}
{Vivado's \texttt{program\_hw\_cfgmem}, with \texttt{PROGRAM.SKIP\_QE\_BIT\_ERASE} at its
default,~0, clears the S25FL256S's non-volatile Quad Enable bit, bit~1 of configuration
register~1. The factory bitstream reads the flash four bits wide (opcode \texttt{0x6C} in its
BSPI register) and needs it. A write with an SPIx4 \texttt{.prm} does not set it back:
Vivado's width-specific part names for this chip are for Zynq only, and on a Kintex-7 it
accepts only \texttt{s25fl256sxxxxxx0-spi-x1\_x2\_x4}. Vivado's Tcl has no command that reads
the flash's registers~\cite{ug835}.}
{In \texttt{docs/design/scripts/}, \texttt{board\_flash.tcl write} sets
\texttt{SKIP\_QE\_BIT\_ERASE} to~1, and a write with it kept the bit;
\texttt{flashregs/FlashRegs.v}, loaded over JTAG, prints SR1, CR1, the chip's ID and the sync
word at \texttt{0x30} on the UART; built with \texttt{WRITE\_REGS=1} it writes CR1 back to
\texttt{0x02}, which repaired the owner's board (``The Quad Enable bit'' in
\texttt{docs/design/figures/README.md}).}

\pitfall{pit:stack}{The stack runs into the program}
{A program that has grown wanders off into garbage after a while, or prints nonsense, with
no warning from the build.}
{In BRAM boot the 6~KB of RAM hold the code, the data and the stack, and the stack grows down
from \texttt{0x1800} into the same space; in flash boot it shares the RAM with the copied code
(Chapter~\ref{ch:flash}). Nothing checks how deep the stack goes.}
{In part. \texttt{firmware\_words} prints how much of the RAM the image fills and refuses one
past \texttt{-max\_addr}, which \texttt{fw/Makefile} sets to the RAM size; set lower, it
reserves room for the stack \notes{firmware\_words arguments; -max\_addr as a stack guard}.
The stack itself is not checked.}

\pitfall{pit:debug-data}{Debug data loaded into the RAM}
{None at run time: mandelbrot runs as it should. The image is larger than its code, though:
\texttt{firmware\_words} reports 852 words, 3\,408 bytes, and \texttt{objdump -D} shows runs of
\texttt{.insn} nonsense after \texttt{\_\_mulsi3} and after \texttt{\_\_modsi3}.}
{\texttt{fw/bram.ld} keeps the catch-all \texttt{*(.*)} of~\cite{levy-learnfpga}, which
places every section of every input file in the RAM. Ubuntu's \texttt{libgcc.a} carries
DWARF debug sections in its members, so those of \texttt{muldi3.o} and \texttt{div.o} land
right after their code: 1\,084 bytes, almost a third of the image and 18\,\% of the 6~KB,
never fetched but taken from the room the stack grows into (pitfall~\ref{pit:stack}). The
\texttt{/DISCARD/} line drops only \texttt{.riscv.attributes} and \texttt{.comment}, which
caused the same trouble before. \texttt{fw/spiflash.ld} names its input sections and is not
affected.}
{Not handled; the committed image is the one this report describes. Adding
\texttt{*(.debug*)} to \texttt{/DISCARD/} gives a 2\,324-byte image; only \texttt{div.o}'s
routines move, \texttt{\_\_divsi3} from \texttt{0xaa0} to \texttt{0x860}, and the calls to
them with it \notes{bram.ld line by line; the /DISCARD/ workaround}.}

\section{Extensions, ranked}

The list is ranked by what each extension gains for the work it takes, the ones others build
on first. None is begun; each names where it enters the design and which pitfalls lie on the
way.

\begin{enumerate}[leftmargin=*, itemsep=2pt]
  \item \textbf{Pipelining.} An instruction takes four to six cycles
    (Table~\ref{tab:cycles}); a five-stage pipeline retires close to one a cycle, a gain of four
    to six on code bound by computation. It needs a second memory port, which the block RAM
    has, forwarding and a stall after a load, a flush on a taken branch, and a stall of the
    whole pipeline while \texttt{mem\_rbusy} is high. The stages split the worst path
    (pitfall~\ref{pit:worst-path}). The golden trace's cycle count will change, and its bytes
    must not: a new golden trace, with \texttt{make golden} and the reason. In flash boot every
    fetch costs 382 cycles, so there a small instruction cache in front of \texttt{SPIFlash}
    gains more than a pipeline.
  \item \textbf{The M extension.} Every \texttt{*}, \texttt{/} and \texttt{\%} in C is a call
    into \texttt{libgcc} today (Section~\ref{sec:xip}), and
    mandelbrot multiplies in its inner loop. The device's DSP blocks, none of them used, multiply
    32 by 32 bits in a few cycles, and a divider fits the FSM as one more state that holds like
    the waits. The firmware then builds with \texttt{-march=rv32im}.
  \item \textbf{UART receive.} \texttt{uart\_tx\_in}, pin Y20, is wired and unused. A receiver
    mirrors \texttt{UartTx}, and a data register and a ready bit take the next IO address bit,
    bit~5 (Section~\ref{sec:memmap}), with their firmware copies added to lint rule~8. It allows
    a serial boot loader: a new program in the RAM without a new bitstream or a flash write.
    Mind the pin names (pitfall~\ref{pit:uart-pins}).
  \item \textbf{Interrupts.} They need the control and status registers of Zicsr, at least
    \texttt{mstatus}, \texttt{mtvec}, \texttt{mepc} and \texttt{mcause}; today their opcode
    stops the core (Appendix~\ref{app:isa}). A timer and the UART receiver are the natural first
    sources. They touch \texttt{Decoder}, \texttt{Control}, which needs a trap state, and the
    \texttt{pc} multiplexer of \texttt{Processor}.
  \item \textbf{DDR3.} The board's 1~GB comes through AMD's Memory Interface Generator, with a
    clock domain of its own and a latency of tens of cycles. The bus already waits on reads,
    through \texttt{mem\_rbusy}, but has no way to stall a write, and without a cache every
    access pays the latency.
  \item \textbf{HDMI.} A pixel clock, TMDS encoding through the output serialisers, and a frame
    buffer: 300~KB for 640 by 480 pixels at 8 bits, which fits in the device's 2~MB of block RAM
    but belongs in DDR3, which is why it comes last.
\end{enumerate}

\chapter{Conclusions}
\label{ch:concl}

The project set out to run compiled C on a processor of its own, on a real board, and to
understand every layer in between. It did. A multi-cycle RV32I core of \implLUTs{} LUTs, with
6~KB of RAM, three IO registers and a flash controller, runs at the Genesys~2's 200~MHz with
\implWNS~ns to spare, draws the Mandelbrot set over the UART from the block RAM, and renders a
ray-traced picture in place from the flash. Every stage from the C source to the UART bytes is
shown with a real excerpt, and every figure a script can make is made by one.

Three things the results show are worth stating plainly. First, the simulation is a faithful
stand-in for the board: the frame the board sent is byte for byte the golden trace's, and its
time matches the trace's cycle count to a fraction of a percent, so a change that keeps the
trace keeps the hardware's behaviour, and the RTL can be restructured against the trace alone.
Second, the core is not what limits these demos; the UART is. A byte takes 87~\textmu s, and a
frame is nearly all bytes, so a pipelined core or a multiplier would change nothing visible
until the output path changes with it. Third, most of the time lost went to things outside the
core: the board's net names, the working directory a tool runs in, Verilog's signedness rules,
the flash clock's hand-over after configuration, and a bit in the flash's configuration
register. Chapter~\ref{ch:next} records each of them with its symptom, so that the next student
loses hours where this project lost days.

What is left is also recorded. Flash boot needs a press of the reset button after each load
(pitfall~\ref{pit:first-fetch}), and a candidate fix is described but not kept; the stack is
unguarded (pitfall~\ref{pit:stack}), and the firmware image carries debug data it never
fetches (pitfall~\ref{pit:debug-data}); thirteen of RV32I's instructions are executed by no
gate; and ST\_NICCC, the demo that would end the report on its most striking picture, waits
for two flash writes. Beyond those, Chapter~\ref{ch:next} ranks the extensions: pipelining
first, then the M extension, UART receive, interrupts, DDR3 and HDMI, each with the part of
the design it enters and the pitfall that lies on its way. The board has room for all of them.

The flash chip itself (Figure~\ref{fig:flash-layout}) holds the bitstream from
\texttt{0x000000} to \texttt{0xAE9E0F}, ST\_NICCC's scene data from \texttt{0xC00000}, and the
code window from \texttt{0xD00000} to \texttt{0xFFFFFF}; the core cannot reach the chip's upper

\chapter{ISA coverage}
\label{app:isa}

The core executes the RV32I base integer instruction set~\cite{riscv-isa}, and the firmware is
built with \texttt{-march=rv32i -mabi=ilp32}, so the compiler emits nothing else.
Table~\ref{tab:app-isa} gives each instruction of RV32I and what the core does with it.

\begin{table}[htbp]
  \centering
  \small
  \begin{tabular}{@{}>{\raggedright\arraybackslash}p{2.9cm}
      >{\raggedright\arraybackslash}p{6.5cm}>{\raggedright\arraybackslash}p{4.5cm}@{}}
    \toprule
    Class & Instructions & In this core \\
    \midrule
    Register & \texttt{ADD SUB SLL SLT SLTU XOR SRL SRA OR AND} & executed, 4 cycles \\
    Immediate & \texttt{ADDI SLTI SLTIU XORI ORI ANDI SLLI SRLI SRAI} & executed, 4 cycles \\
    Upper immediate & \texttt{LUI AUIPC} & executed, 4 cycles \\
    Jump & \texttt{JAL JALR} & executed, 4 cycles \\
    Branch & \texttt{BEQ BNE BLT BGE BLTU BGEU} & executed, 4 cycles \\
    Load & \texttt{LB LH LW LBU LHU} & executed, 6 cycles \\
    Store & \texttt{SB SH SW} & executed, 5 cycles \\
    Fence & \texttt{FENCE} & a no-op, without being decoded \\
    System & \texttt{ECALL EBREAK} & stop the core \\
    \bottomrule
  \end{tabular}
  \caption{RV32I in this core. The cycles are from the RAM (Table~\ref{tab:cycles}); a word
    fetched or loaded from the flash adds an SPI transaction.}
  \label{tab:app-isa}
\end{table}

\paragraph{FENCE.} Its opcode sets none of \texttt{Decoder}'s class flags, so the core treats
it as an ALU instruction: \texttt{EXECUTE} advances \texttt{pc} and writes the ALU's output to
the instruction's \texttt{rd} field, which is \texttt{x0} in a \texttt{FENCE}. With one core,
no cache and memory accessed in program order, a no-op is all a \texttt{FENCE} has to do.
\texttt{FENCE.I} shares the opcode, and is a no-op too, also correctly: instructions and data
come from the same memory, uncached.

\paragraph{ECALL and EBREAK.} \texttt{EXECUTE} leaves \texttt{pc} unchanged for the SYSTEM
opcode, so the core fetches the instruction again, forever: a halt that the reset button
ends. The start-up code ends with \texttt{EBREAK}, should \texttt{main} return.

\paragraph{Left out.} No extension: no M, A, F, D or C, and no Zicsr. The CSR instructions
share the SYSTEM opcode and stop the core as \texttt{ECALL} does, though one whose \texttt{rd}
is not \texttt{x0} also writes the ALU's output to it on every pass. No privilege modes, no
exceptions and no interrupts: an illegal instruction is executed as \texttt{FENCE} is, its ALU
output written to its \texttt{rd} field, and a misaligned load or store is not trapped either.
It takes its lanes from the aligned word around its address, so its result is wrong, though
code built from C never makes one for aligned data.
