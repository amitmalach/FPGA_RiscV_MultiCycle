\chapter*{Abstract}

This report describes a small system on chip built around a multi-cycle RV32I core, written
in Verilog and run at 200~MHz on the Kintex-7 FPGA of a Digilent Genesys~2 board. The core
executes the RV32I base integer instruction set, one instruction at a time, in four to six
clock cycles each, under a seven-state finite state machine. Around it sit 6~KB of block RAM,
a memory-mapped LED register, a UART transmitter and a controller for the board's 32~MB QSPI
flash, all on one bus that the core sees as plain memory. Two boot modes share the same
hardware. In BRAM boot the firmware image is part of the bitstream and the program runs from
the RAM. In flash boot the core executes a program in place from the flash, which admits
programs larger than the RAM at about a hundredth of the speed.

On the board the design draws the Mandelbrot set and a turning RISC-V logo over the UART from
its block RAM, renders tinyraytracer's ray-traced picture, a program five times the RAM's
size, in place from the flash, and plays the ST-NICCC polygon demo from scene data in the
flash. The design is inspired by Bruno Levy's \emph{From Blinker
to RISC-V} series.

\chapter{Introduction}
\label{ch:intro}

This is an undergraduate project with one aim: to build a processor that runs compiled C on a
real FPGA board, and to understand every layer between the C source and the lit LED. The
result is a multi-cycle RV32I core, 6~KB of RAM, three memory-mapped IO registers and a flash
controller, wired into one top level and run on a Digilent Genesys~2 at the board's 200~MHz
clock. This chapter shows what the board does with it, then what was built and how the report
is laid out.

\section{What the board does}
\label{sec:showcase}

Every picture in this section is rendered from bytes the board sent over its UART. From the
moment a bitstream starts to load over JTAG, the host records the UART at 115\,200~baud,
8N1, with a timestamp on every read, accurate to about 2~ms. The raw captures are committed
in \texttt{docs/design/captures/}, and \texttt{make figures} renders the figures from them.
The demos draw with ANSI escape sequences, each pixel a coloured terminal cell, so a serial
terminal shows them as pictures. The code on the right of each figure holds the address of
the repository's README, \url{\demourl}, where every demo below plays as an animation.

\paragraph{Mandelbrot.} The Mandelbrot set is the set of complex numbers $c$ for which the
sequence $z_0 = 0$, $z_{n+1} = z_n^2 + c$ stays bounded. A program draws it by taking each
pixel as a point $c$ of the complex plane and iterating the sequence until $|z_n|$ exceeds~2,
which proves that it escapes, or until a limit on the steps is reached. The pixel's colour
comes from the number of steps it took, and the points that never escape form the set. Its boundary is a
fractal: every enlargement of it shows new detail. The committed firmware image draws the set
from the block RAM, for $-2 \le \mathrm{Re}\,c, \mathrm{Im}\,c \le 2$, in fixed-point
arithmetic with at most 20 steps a pixel. It sends one frame of 46 by 46 pixels a second, steps
the colours by one at each frame, and counts the frames on the LEDs.
Figure~\ref{fig:board-mandelbrot} shows the first five of the 23 frames captured, which cover
a full cycle of the 21 colours.

The first frame the board sent was compared with two references, and it is identical to both,
byte for byte: the frame that the simulation of the design produced (the golden trace,
Section~\ref{sec:golden}), and the output of the same C program compiled and run on a PC. The
board, the simulation and the C source therefore agree. The frame took 1031.3~ms on the board,
from its first byte to the first byte of the next. The simulation counted 206\,292\,808
cycles for it, 1031.46~ms at 200~MHz, so the board runs the cycles the simulation counts, to
within the timestamps' accuracy. Most of a frame is the UART. Sending its 11\,014 bytes at
ten bits a byte takes about 956~ms, and \texttt{putchar} waits for each byte to leave, so the
computation itself takes about 75~ms.

\paragraph{tinyraytracer.} tinyraytracer is Dmitry Sokolov's small ray
tracer~\cite{sokolov-tinyraytracer}, a few hundred lines written to teach how a ray-traced
picture is made. For each pixel it casts a ray from the eye through the screen, finds the
nearest sphere or floor point the ray hits, and colours it from three point lights, with
diffuse and specular shading and shadows. Rays that hit the mirror or the glass sphere are
reflected or refracted and traced again. Bruno Levy ported it to C for his FemtoRV
core~\cite{levy-learnfpga}, and this project replaced the port's display layer with ANSI output
to the terminal. It is 29\,016 bytes of code and constants, five times the RAM, so it runs in
flash boot: every instruction is fetched in place from the board's flash, and every
floating-point operation is a call into \texttt{libgcc}. The board drew the picture a pixel at
a time, row by row, in 126.8~s, 110~ms a pixel, and Figure~\ref{fig:board-tinyraytracer} shows
it as it grew. The run is 21\,412 bytes long and is, byte for byte, what
\texttt{fw/tinyraytracer.c} prints when compiled natively, with floating point in software on
the board and in the host's hardware on the PC. The board printed nothing until the CPU RESET
button was pressed after the load (pitfall~\ref{pit:first-fetch}), and the first write of its
image to the flash cost the board its power-on boot until the flash's Quad Enable bit was set
again (pitfall~\ref{pit:quad-enable}).

\paragraph{sieve.} The sieve of Eratosthenes finds the primes below a bound by crossing out
the multiples of each prime in turn: whatever is never crossed out is prime. The sieve demo,

\paragraph{ST\_NICCC.} ST-NICCC~2000 is a demo for the Atari~ST by the group Oxygene whose
best-known part is a flight through a scene of flat-shaded polygons, streamed from disk. Its
scene file was later published for a competition to replay it on other
machines~\cite{stniccc}. Each frame of the file lists polygons, each with a colour from a
palette of 16 and the screen points of its corners. Bruno Levy's player,
\texttt{fw/ST\_NICCC.c}, reads the file a word at a time through the core's flash region,
decodes each frame and fills its polygons as runs of coloured cells, 128 by 50 cells for the
scene's 256 by 200 points. The file is 640~KB, a hundred times the RAM, so it was written to
the flash at \texttt{0xC00000}, where Figure~\ref{fig:flash-layout} reserves room for it, and
the player runs from the block RAM in BRAM boot. The board sent 1.7~MB in 150~s, 11.4~kB/s,
the UART's full rate, and drew a frame every 0.9~s. The player never clears the screen: each
frame is drawn over the last, so a screen taken in the middle of a frame shows parts of two.

The run is also the clearest evidence behind pitfall~\ref{pit:first-fetch}. Its first frame
came out wrong, as a wrong first word from the flash makes it: the first SPI transaction after
configuration loses clock edges (Section~\ref{sec:cclk}). The polygons were right again from
1.3~s on, and one palette colour stayed wrong until the scene set it again, 70~s in. From
there to the end of the capture, the 917~KB the board sent are byte for byte what
\texttt{fw/ST\_NICCC.c} prints when compiled natively with the same scene file.

\section{Starting point and own work}

The project started from Bruno Levy's \emph{learn-fpga} series \emph{From Blinker to
RISC-V}~\cite{levy-learnfpga}, which grows a multi-cycle RV32I core in small increments,
through memory-mapped IO and the GNU toolchain to execution from SPI flash, for small boards
such as the IceStick and the ULX3S. The series supplied the starting point: the shape of the
state machine, the bus and the demo programs. Taking that starting point to a working, verified
system on the Genesys~2, a board the series does not support, was the project's own work,
and most of the effort went there.

\begin{itemize}[leftmargin=*, itemsep=2pt]
  \item \textbf{The port to the Genesys~2.} The differential 200~MHz clock, the pin
    constraints, the board's UART pin names (pitfall~\ref{pit:uart-pins}), and the flash's
    clock, which a 7-series device reaches only through \texttt{STARTUPE2}
    (Section~\ref{sec:cclk}).
  \item \textbf{The flash layout and flash boot.} A layout designed around the 11~MB
    bitstream and the factory demo the board keeps, with bit~24 as the flash's region bit, the
    code window at \texttt{0xD00000}, and the linker script and start-up code that copy the
    hot code into the RAM (Chapter~\ref{ch:flash}).
  \item \textbf{The RTL, restructured and debugged.} Eleven modules, one per file, with the
    memory map defined once and every copy of it checked. The bugs found and fixed include
    the arithmetic shift that shifted logically (pitfall~\ref{pit:sra}) and a simulation hang
    in the flash controller (pitfall~\ref{pit:init-values}), and the design notes record the
    reason behind every subtle choice, such as the reset state
    (pitfall~\ref{pit:reset-wait-data}).
  \item \textbf{The verification.} The golden trace and the regression, the ALU unit bench,
    ten lint rules, and the hooks that hold every commit to its gates
    (Chapter~\ref{ch:verif}).
  \item \textbf{The board work.} The build flow from C to the board in both boot modes, the
    scripts that capture every demo's output and check it against the PC, and a small design
    of its own that read and repaired the flash's Quad Enable bit
    (pitfall~\ref{pit:quad-enable}).
  \item \textbf{The analysis.} The timing, utilisation and power of the routed design
    (Chapter~\ref{ch:results}), and this report, whose figures are generated by scripts from
    the real build and the real board.
\end{itemize}

\section{What was built}

The hardware is eleven Verilog modules, one per file, in one clock domain
(Chapter~\ref{ch:arch}). The core sees a single bus, a 32-bit address with a read strobe,
write data with a byte mask and a busy input. \texttt{IOBus} decodes it into three regions by
one address bit each: the RAM, the IO registers and the flash. The RAM is 6~KB of block RAM
shared by instruction fetch and data. The IO registers are the LEDs, the UART's data register
and its status word, and the flash controller turns a read in flash space into one SPI transaction
and holds the core busy for its length.

The core (Chapter~\ref{ch:core}) executes RV32I and nothing beyond it: no multiplier, no
interrupts, no control and status registers. An instruction takes four cycles, a store five
and a load six, each cycle a memory or register-file read answered one cycle after it is
asked. The same hardware boots two ways (Chapter~\ref{ch:flash}): in BRAM boot the firmware
image is read into the block RAM when the bitstream is synthesised. In flash boot the reset
vector points into the flash and the core fetches each instruction from there in place.

The firmware (Chapter~\ref{ch:flow}) is six demos in C and assembly, built by the RISC-V GCC
with a start-up file and a linker script per boot mode. The repository
(Chapter~\ref{ch:repo}) holds the RTL, the firmware, the simulation, the Vivado scripts and
this report, with make targets that build and check all of it. Verification
(Chapter~\ref{ch:verif}) is an ALU unit bench, a golden trace that the regression must
reproduce byte for byte and cycle for cycle, and a lint. Each is a gate whose log a commit
cites.

\section{Results in brief}
\label{sec:results-brief}

\begin{itemize}[leftmargin=*, itemsep=2pt]
  \item \textbf{Size and speed.} The routed design is \implLUTs{} LUTs, \implFFs{} flip-flops
    and two block RAM tiles, under half a percent of the XC7K325T. The 200~MHz clock is met
    with \implWNS~ns of slack on the worst path, the load path (Chapter~\ref{ch:results}).
  \item \textbf{The board, the simulation and the source agree.} The first mandelbrot frame
    the board sent is byte for byte the golden trace's UART output, which is byte for byte
    what the C program prints when compiled natively. The board's frame time matches the
    simulated cycle count at 200~MHz to within 0.2~ms (Section~\ref{sec:showcase}).
  \item \textbf{Flash boot works}, with one press of the reset button after each load, which
    pitfall~\ref{pit:first-fetch} explains.
  \item \textbf{The demos are bound by the UART.} At 115\,200~baud a byte takes 87~\textmu s,
    and the mandelbrot frame spends about 956 of its 1031~ms sending. A faster core would not
    show on these demos.
  \item \textbf{Ten pitfalls are recorded}, P1 to P10 in Chapter~\ref{ch:next}, each with
    its symptom, its cause and where it is now handled. The costliest were outside the core.
\end{itemize}

\paragraph{The oscillator (Figure~\ref{fig:sch-oscillator}).} IC23, a DSC1103 oscillator,
takes the 3.3~V supply, VCC3V3, on its VDD pin, with two 100~nF capacitors, C159 and C160, to
ground beside it to keep the supply clean. Its enable pin, EN, is tied to the supply, so it
runs from power-on. Its two outputs, OUT and its complement on pins 4 and~5, drive the nets
\texttt{SYSCLK\_P} and \texttt{SYSCLK\_N}, an LVDS pair: the clock is the difference between
the two lines, not the level of either, and R309, 100~$\Omega$ across the pair, is the line's
termination. The pair reaches the FPGA on AD12 and AD11, a clock-capable pin pair, so the
clock enters through \texttt{IBUFDS} (Section~\ref{sec:clock}).

\paragraph{The reset button (Figure~\ref{fig:sch-reset}).} BTN1 connects a node to ground
while it is pressed. R293, 10~k$\Omega$, pulls that node up to 3.3~V, so it reads~1 while the
button is up, and R294, 10~k$\Omega$ in series, carries it to the net \texttt{CPU\_RESET\_N}
on FPGA pin R19. The net is low only while the button is pressed, as the \texttt{\_N} in its
name says, hence the design's active-low reset.

\paragraph{The LEDs (Figure~\ref{fig:sch-leds}).} Eight identical branches: each net,
\texttt{LED0} to \texttt{LED7}, comes from an FPGA pin, passes a 330~$\Omega$ resistor and
the LED, and ends on the common ground at the right. So an LED lights while its pin is high,
and the resistor limits its current to a few milliamperes. The pin follows one bit of the design's LED register
(Section~\ref{sec:memmap}): a store that writes 1 to bit~$i$ lights LD$i$, and 0 puts it out.

\paragraph{The USB-UART bridge (Figure~\ref{fig:sch-uart}).} On the left, J15 is the micro-USB
connector. Its data lines, D+ and D$-$, run to IC16, the FT232RQ bridge, past D17, a diode
array that protects them from static discharge. Its supply line, V, carries the PC's 5~V, and
the divider R255 and R258 on it drives the bridge's RESET input, so the bridge runs only while
a PC powers the cable. The connector's shield goes to ground through R254 and C116. On the
right, the bridge's TXD output drives the net \texttt{UART\_TX}, the PC's transmit line toward
the FPGA, and its RXD input receives \texttt{UART\_RX\_OUT}, the FPGA's transmit line, the one
this design drives. The board's net names take the PC's view for TX and RX and the FPGA's for
in and out, and mixing the two up is pitfall~\ref{pit:uart-pins} \notes{UART port names and
the pin-direction trap}. CBUS0 and CBUS1 light the activity LEDs, LD13 (TX) and LD12 (RX),
through 470~$\Omega$ from the bridge's own 3.3~V output, \texttt{FT232R3V3}. The modem lines,
RTS to RI, are left unconnected, as the crosses mark.

\paragraph{The mode jumper (Figure~\ref{fig:sch-mode}).} JP5 is a row of four pins: ground,
the net \texttt{MODE2}, the 3.3~V supply and the net \texttt{MODE1}. Each mode net has a
1~k$\Omega$ resistor: R335 pulls \texttt{MODE2} up, R339 pulls \texttt{MODE1} down, and R337
holds \texttt{MODE0} high. The jumper shorts one pair of pins, and the three drawings on the
left show its positions. On pins 1 and~2 it grounds \texttt{MODE2}, so $M[2{:}0]=001$, Master
SPI: the FPGA configures itself from the flash, which on the owner's board holds Digilent's
factory demo at offset~0, left untouched. On pins 2 and~3 it raises \texttt{MODE2}, so
$M[2{:}0]=101$, JTAG: the FPGA waits for a bitstream. On pins 3 and~4 it raises \texttt{MODE1},
so $M[2{:}0]=111$, Slave Serial, which the board's USB and microSD configuration
uses~\cite{ug470}. The FPGA reads the mode pins when configuration starts, at power-on or after
a press of PROG. The second micro-USB port is Digilent's USB-JTAG circuit: Vivado's hardware
manager loads every bitstream of this report through it, and writes the flash through it,
whatever the jumper says.

\paragraph{The configuration bank and the flash (Figure~\ref{fig:sch-config}).} On the left
is IC22O, the part of the FPGA's symbol that holds bank~0, its dedicated configuration pins,
labelled PROG, with a few pins of bank~14. On the symbol's right are the JTAG pins, TMS, TCK,
TDI and TDO, the mode pins M0 to M2 from the jumper, \texttt{CCLK\_0} on B10, which is the
flash clock \texttt{QSPI\_SCK}, and \texttt{DONE}, \texttt{PROGRAM\_B} and \texttt{INIT\_B}.
The resistors in the middle pull those three up to 3.3~V. \texttt{DONE} also lights LD14
through R334 once configuration has ended, and the PROG button, BTN2, grounds
\texttt{PROGRAM\_B}, which clears the FPGA and starts its configuration again. On the left,
\texttt{CFGBVS\_0}, tied high through R331, tells the FPGA that its configuration banks run at
3.3~V, as the constraints file's \texttt{CFGBVS} and \texttt{CONFIG\_VOLTAGE} say too. The
bank~14 pins at the bottom right are dual-purpose: P24, \texttt{D00\_MOSI}, is
\texttt{QSPI\_D0}, R25, \texttt{D01\_DIN}, is \texttt{QSPI\_D1}, and U19, \texttt{FCS\_B}, is
\texttt{QSPI\_CSN}, the pins the design drives as \texttt{spiflash\_mosi},
\texttt{spiflash\_miso} and \texttt{spiflash\_csn}. Three of the LEDs are on the same bank.
On the right is IC26, the S25FL256S flash. \texttt{QSPI\_D0} enters its SDI/DQ0 pin and
\texttt{QSPI\_D1} leaves its SDO/DQ1 pin, both through 0~$\Omega$ resistors, the clock enters
SCK, and chip select enters CS, which R320 holds high, deselected, while nothing drives it.
R328 and R327 pull WP/DQ2 and HOLD/DQ3 high, so in this design's one-bit SPI the flash is
neither write-protected nor paused. The flash sits on the configuration pins so that the FPGA
can read its bitstream from it at power-on, and its clock is the dedicated CCLK pin, which a
design reaches only through \texttt{STARTUPE2} (Section~\ref{sec:cclk}). At the top, the
buffer IC25D passes the bridge's \texttt{UART\_TX} to the FPGA as \texttt{UART\_TX\_IN}.

\section{The bus and the modules}

The core, \texttt{Processor}, sees one bus and nothing else: a 32-bit byte address, a
one-cycle read strobe, 32 bits of read data, 32 bits of write data with a four-bit byte
mask, and a busy input. There is no acknowledge. A read requested with \texttt{mem\_rstrb}
is answered on \texttt{mem\_rdata} in the next cycle unless \texttt{mem\_rbusy} is high, and
a write lands on the edge where \texttt{mem\_wmask} is non-zero. Every address falls in
some region, so no access is refused \notes{Processor bus has no notion of RAM versus
device}.

Everything around the core follows from that contract. \texttt{IOBus} decodes the address
into three regions, forwards the strobe and the mask to the RAM, holds the LED register,
turns a store into the UART's send pulse and a flash read into an SPI transaction, and
multiplexes the read data back. \texttt{Memory} is 6~KB of block RAM with one port, shared
by instruction fetch and by loads and stores. Its read is registered, which is why the core
waits a cycle after every read, and its write lands on the same edge, which is why a store
needs no wait \notes{Read and write timing are not symmetric}. \texttt{UartTx} sends 8N1 at
115\,200~baud and \texttt{SPIFlash} reads one 32-bit word per transaction, at a sixth of the
system clock. The flash controller is the only block that stalls the core, by holding
\texttt{mem\_rbusy} for the length of a transaction \notes{Only flash reads stall the core,
read mux}. \texttt{Clockworks} is among the instances of Figure~\ref{fig:rtl-soc} but
contributes no cell to the netlist, as Section~\ref{sec:clock} explains.

A region is chosen by one address bit, not by a comparator: bit~24 selects the flash, bit~22
the IO registers when bit~24 is clear, and an address with neither set is RAM. Inside the IO
region each register owns one bit as well, so a store to \texttt{IO\_BASE + 4} lights the
LEDs and a store to \texttt{IO\_BASE + 8} sends a byte. The whole decode is a few bit tests
in \texttt{IOBus} \notes{Address decode: one bit per region, one-hot IO registers, why bit
24}. Bit~24 was chosen with care: everything below the selector bit is the offset inside
the flash, and bit~23 would leave 8~MB, short of the 10.9~MB bitstream at the start of the
chip, while bit~24 leaves 16~MB, exactly the three address bytes of the flash's \texttt{03h} read
command.

Three consequences matter when writing firmware. Nothing is rejected: an address past the
RAM's 6~KB still selects the RAM, and what such an access does is undefined. Only the UART
status register answers a read, and every other IO address reads as zero. And a write to flash
space does nothing. To add a peripheral, give it the next free bit of the IO word address,
bit~5 at byte offset \texttt{0x20}, decode it in \texttt{IOBus} as the three existing ones
are decoded, add it to the read mux if it answers reads, and add its copy in
\texttt{fw/io.h} to the lint rule.

\section{Clock and reset}
\label{sec:clock}

The board's 200~MHz oscillator drives a differential pair, so the clock enters through
\texttt{IBUFDS} and \texttt{BUFG} \notes{Genesys 2 differential clock input}. That net,
\texttt{clk}, is the only clock in the design, and its 5~ns period is the one timing
constraint (Chapter~\ref{ch:results}).

\texttt{Clockworks} derives two signals from the clock and the button. \texttt{clk\_enable}
is a gearbox: with the parameter \texttt{SLOW} set to $n$, it is high for one cycle in
$2^n$, and the core, the bus and the RAM advance only on those cycles, while the UART and
the flash controller run every cycle, so the baud rate and the SPI clock stay right
\notes{Gearbox counter}. The shipped design sets it to~0, \texttt{clk\_enable} is the
constant~1, and the module synthesises to nothing.

\texttt{reset\_n} is the CPU RESET button, active-low, forwarded as it is: no synchroniser
and no debounce. Every reset is synchronous, and three places have one: the core's
\texttt{pc}, \texttt{instr} and FSM state, the LED register, and the UART's transmitter
\notes{Synchronous reset and the clock enable}. The core's registers also declare their
reset value as their initial value, which is what configuration loads into a 7-series
flip-flop, so the core leaves configuration in its reset state and starts without a press of
the button \notes{Power-on state matches the reset state}. In flash boot a press is still
needed on the board, for a reason in the flash controller's start-up
(pitfall~\ref{pit:first-fetch}). The FSM resets into \texttt{WAIT\_DATA}, which asserts no
strobe and falls through to \texttt{FETCH\_INSTR}, not into \texttt{FETCH\_INSTR} itself, and
pitfall~\ref{pit:reset-wait-data} gives the reason.

\chapter{The RV32I instruction set}
\label{ch:isa}

RV32I is the base integer instruction set of RISC-V~\cite{riscv-isa}, the one this core
executes and the one the firmware is compiled for, with \texttt{-march=rv32i -mabi=ilp32}. It
has 32 registers of 32 bits and 40 instructions, each one 32 bits long. It is a load-store
architecture: only the loads and the stores touch memory, and every other instruction works on
registers and constants. This chapter gives what the later chapters rely on: the registers,
how an instruction is written, how its 32 bits are laid out, and what each instruction does in
this core.

\section{Registers and assembly syntax}
\label{sec:isa-regs}

The registers are \texttt{x0} to \texttt{x31}. \texttt{x0} always reads as zero, and a write
to it is discarded, which makes it useful as a source of zero and as a destination for a
result nobody needs. The program counter, \texttt{pc}, is separate and is not one of the 32.
The calling convention gives each register a role and an ABI name, the name the compiler and
the disassembler print (Table~\ref{tab:isa-regs}).

\begin{table}[!ht]
  \centering
  \small
  \begin{tabular}{@{}lll@{}}
    \toprule
    Registers & ABI names & Role \\
    \midrule
    \texttt{x0} & \texttt{zero} & always zero \\
    \texttt{x1} & \texttt{ra} & return address, written by a call \\
    \texttt{x2} & \texttt{sp} & stack pointer, the top of the RAM at start-up \\
    \texttt{x3} & \texttt{gp} & global pointer, set to \texttt{IO\_BASE} by this design's
      start-up code \\
    \texttt{x4} & \texttt{tp} & thread pointer, unused here \\
    \texttt{x5}--\texttt{x7}, \texttt{x28}--\texttt{x31} & \texttt{t0}--\texttt{t2},
      \texttt{t3}--\texttt{t6} & temporaries, which a call may overwrite \\
    \texttt{x8}, \texttt{x9}, \texttt{x18}--\texttt{x27} & \texttt{s0}--\texttt{s1},
      \texttt{s2}--\texttt{s11} & saved registers, which a call preserves \\
    \texttt{x10}--\texttt{x17} & \texttt{a0}--\texttt{a7} & arguments, \texttt{a0} and
      \texttt{a1} also the return value \\
    \bottomrule
  \end{tabular}
  \caption{The 32 registers and their roles in the calling convention.}
  \label{tab:isa-regs}
\end{table}

An instruction is written with its destination first and its sources after it. In
\texttt{add x1, x2, x3}, \texttt{x1} is the destination, \texttt{rd}, and \texttt{x2} and
\texttt{x3} are the two sources, \texttt{rs1} and \texttt{rs2}: the instruction computes
$\texttt{x1} \leftarrow \texttt{x2} + \texttt{x3}$. An instruction with a constant puts it
last: \texttt{addi x1, x2, -5} computes $\texttt{x1} \leftarrow \texttt{x2} - 5$. A load or
a store writes its address as an offset and a base register: \texttt{lw s0, 8(sp)} loads the
word at address $\texttt{sp} + 8$ into \texttt{s0}, and \texttt{sw s0, 4(a5)} stores
\texttt{s0} at address $\texttt{a5} + 4$. A store has no destination register, so its data
register is \texttt{rs2} and its base \texttt{rs1}. A branch names two registers to compare
and a target: \texttt{beq a0, a1, loop} jumps to \texttt{loop} when \texttt{a0} equals
\texttt{a1}.

The assembler also accepts pseudo-instructions, which it turns into real ones:
\texttt{nop} is \texttt{addi x0, x0, 0}, \texttt{mv a0, a1} is \texttt{addi a0, a1, 0},
\texttt{j label} is \texttt{jal x0, label}, \texttt{ret} is \texttt{jalr x0, 0(ra)}, and
\texttt{li} loads a constant with an \texttt{addi}, a \texttt{lui} or both.

\section{Instruction formats}
\label{sec:isa-formats}

Every instruction is one of six formats, R, I, S, B, U and J, which differ in where they keep
their constant, the \emph{immediate} (Figure~\ref{fig:isa-formats}). The fields are:

\begin{itemize}[leftmargin=*, itemsep=2pt]
  \item \textbf{opcode}, bits 6 to~0, the instruction's class: register arithmetic, arithmetic
    with an immediate, load, store, branch and so on. Its two low bits are \texttt{11} in
    every 32-bit instruction.
  \item \textbf{rd}, \textbf{rs1} and \textbf{rs2}, five bits each, the numbers of the
    destination and the two source registers. They sit at the same bit positions in every
    format that has them, so the register file can be read before the instruction is fully
    decoded. This core reads \texttt{rs1} and \texttt{rs2} in \texttt{FETCH\_REGS} for every
    instruction, whether it uses them or not (Chapter~\ref{ch:core}).
  \item \textbf{funct3} and \textbf{funct7}, which choose the operation within a class:
    \texttt{funct3} picks one of the eight ALU operations, the branch condition or the load
    and store width, and bit~30, in \texttt{funct7}, tells \texttt{SUB} from \texttt{ADD} and
    \texttt{SRA} from \texttt{SRL}.
  \item \textbf{imm}, the immediate, a signed constant. Its sign is always bit~31, so it can
    be sign-extended before the format is known. I and S immediates are 12 bits, from $-2048$
    to 2047. B and J immediates are byte offsets with bit~0 left out, since every instruction
    starts at an even address: a branch reaches $\pm$4~KB and \texttt{jal} $\pm$1~MB. A U
    immediate is the upper 20 bits of a 32-bit value.
\end{itemize}

\paragraph{FENCE.} Its opcode sets none of \texttt{Decoder}'s class flags, so the core
treats it as an ALU instruction whose \texttt{rd} is \texttt{x0}: a no-op, which is all a
\texttt{FENCE} has to do with one core, no cache and memory accessed in program order.
\texttt{FENCE.I} shares the opcode and is a no-op too, also correctly: instructions and data
come from the same memory, uncached.

\paragraph{ECALL and EBREAK.} \texttt{EXECUTE} leaves \texttt{pc} unchanged for the SYSTEM
opcode, so the core fetches the instruction again, forever: a halt that the reset button
ends. The start-up code ends with \texttt{EBREAK}, should \texttt{main} return.

\paragraph{Left out.} No extension: no M, A, F, D or C, and no Zicsr. The CSR instructions
share the SYSTEM opcode and stop the core as \texttt{ECALL} does. There are no privilege
modes, no exceptions and no interrupts: an illegal instruction is executed as \texttt{FENCE}
is, and a misaligned load or store is not trapped, so its result is wrong, though code built
from C never makes one for aligned data.

\chapter{The multi-cycle core}
\label{ch:core}

\texttt{Processor} executes RV32I and nothing beyond it: no M extension, no interrupts, no
control and status registers, and \texttt{ECALL} and \texttt{EBREAK} stop the core
(Chapter~\ref{ch:isa}). It is a multi-cycle core: one instruction at a time, several clock
cycles each, one FSM state per cycle. \texttt{Control} is the FSM, \texttt{Decoder},
\texttt{ALU} and \texttt{RegisterFile} are what their names say, and \texttt{Processor} holds
\texttt{pc}, the instruction register and the glue between the other four.

\section{The state machine}

An instruction takes several cycles because the RAM answers a read one cycle after it is
requested, and the register file's read is synchronous too, so each needs a state of its
own \notes{Why one instruction takes several cycles}. Figure~\ref{fig:fsm} shows the seven
states.

\texttt{FETCH\_INSTR} drives \texttt{pc} on the bus with the read strobe,
\texttt{WAIT\_INSTR} latches the word the RAM returns, \texttt{FETCH\_REGS} latches
\texttt{rs1} and \texttt{rs2}, and \texttt{EXECUTE} loads \texttt{pc} with its next value and
writes \texttt{rd} for every instruction but a load, a store or a branch. A load goes on to
\texttt{LOAD}, which drives the data address with the strobe, and \texttt{WAIT\_DATA}, which
writes the returned word to \texttt{rd}. A store goes to \texttt{STORE}, which drives the
address, the data and the byte mask for one cycle. The RAM writes on that same edge, so
there is no wait after a store \notes{STORE needs no wait state}. The two waits are the only
states that can last longer than a cycle: they hold while \texttt{mem\_rbusy} is high, which
only the flash controller raises \notes{Instruction fetch stalls on mem\_rbusy}.

\texttt{Control} decodes four one-cycle strobes from the state, \texttt{latch\_instr},
\texttt{read\_regs}, \texttt{update\_pc} and \texttt{write\_rd}, already qualified with
\texttt{clk\_enable} and \texttt{reset\_n}. \texttt{write\_rd} in \texttt{WAIT\_DATA} is
gated by \texttt{mem\_rbusy} as well, or a stalled flash load would write the bus's garbage
to \texttt{rd} on every stalled cycle \notes{Write-back enable gated by mem\_rbusy in
WAIT\_DATA}. Table~\ref{tab:cycles} gives the cost per instruction class.

Two of the four cycles of the commonest class are the fetch. A pipelined core would overlap

a gain of four to six on code bound by computation. The demos of Section~\ref{sec:showcase} are
bound by the UART, so for them the multi-cycle core costs nothing visible. Pipelining is the
first extension in Chapter~\ref{ch:next}.

\section{The datapath}

\texttt{Decoder} is purely combinational on the instruction register: the ten class flags
from the opcode, disjoint, so exactly one is high for every instruction the core implements,
the register indices and the \texttt{funct3} and \texttt{funct7} fields, and the five
immediates of Figure~\ref{fig:isa-formats}, sign-extended from bit~31. It also settles the two meanings of
\texttt{funct7[5]}: a subtraction only in the register form, since an \texttt{ADDI} whose
immediate happens to set bit~30 must still add, and an arithmetic shift in both forms
\notes{ADD versus SUB: funct7[5] alone is not enough}.

\texttt{RegisterFile} is the 32 integer registers in LUT RAM: a synchronous read of
\texttt{rs1} and \texttt{rs2} on \texttt{read\_regs}, a synchronous write of \texttt{rd} on
\texttt{write\_rd}, and \texttt{x0} never written and read as zero explicitly \notes{x0
reads as zero explicitly}. \texttt{ALU} is combinational (Figure~\ref{fig:rtl-alu}): its
second operand is \texttt{rs2} for register instructions and the I-immediate for everything
else, \texttt{funct3} picks one of the eight operations, and a second case on
\texttt{funct3} computes the six branch conditions, with a default of zero so that no latch
is inferred \notes{Branch comparator default arm}. Both arms of the right shift are signed,
or \texttt{SRA} shifts logically (pitfall~\ref{pit:sra}).

The rest of \texttt{Processor} is the glue between these. A multiplexer chooses the next
\texttt{pc}: the branch target when a branch is taken, the jump target for \texttt{JAL},
\texttt{rs1} plus the immediate with bit~0 cleared for \texttt{JALR}, otherwise
\texttt{pc + 4}. An adder forms the load or store address from \texttt{rs1} and the I- or
S-immediate. The memory moves whole words, so a byte or halfword load picks its lane by the
address's low two bits and sign-extends unless \texttt{funct3[2]} says not to, and a store
broadcasts \texttt{rs2} into every lane it could land in and lets the byte mask select
\notes{Store data is broadcast to every lane, the mask selects}. The write-back multiplexer
gives \texttt{rd} its value: \texttt{pc + 4} for the jumps, the U-immediate for
\texttt{LUI}, \texttt{pc} plus it for \texttt{AUIPC}, the aligned load data, or the ALU
result. The design's worst timing path runs through this glue, from the instruction register
through the load-store address adder, the region decode and the load lanes to the register
file's write port (pitfall~\ref{pit:worst-path}).

The load takes cycles 0 to~5. In \texttt{FETCH\_INSTR} the bus address is \texttt{pc},
\texttt{0x278}, with the strobe. In \texttt{WAIT\_INSTR} the RAM answers with the
instruction word, \texttt{0x00812403} (Figure~\ref{fig:isa-formats}), and \texttt{latch\_instr} moves it into
\texttt{instr}. From then on the bus address is the load-store address, \texttt{sp + 8}.
\texttt{EXECUTE} advances \texttt{pc} to \texttt{0x27c}, \texttt{LOAD} asserts the strobe at
the data address, and \texttt{WAIT\_DATA} sees the word,~0, and \texttt{write\_rd} writes it to
\texttt{s0}. The two \texttt{LUI}s take four cycles each, writing \texttt{rd} in
\texttt{EXECUTE}. The store, cycles 14 to~18, writes no register. In \texttt{STORE} the bus
carries the LED register's address, \texttt{0x400004}, the byte mask \texttt{f} and the
data, and the register takes the value on the edge that ends the window. Each read is
answered one cycle after its strobe, and no cycle is spent on the store: the two facts about
the memory that shaped the FSM.

\chapter{Memory and memory-mapped IO}
\label{ch:memio}

To the core the three regions of the bus differ only in timing. The RAM and the IO registers
answer every read in the next cycle and take every write on the edge it is presented, while the
flash answers a read about 380 cycles later, and the core waits.

\section{The RAM}

\texttt{Memory} is 1536 words, 6~KB, of block RAM: two of the Kintex-7's 445 tiles. Its one
port serves instruction fetch, loads and stores alike, so in BRAM boot the program, its data
and its stack share it, the stack growing down from the top. The read is registered: the
word addressed in the cycle of \texttt{ram\_rstrb} appears on \texttt{ram\_rdata} at the
next edge, which is the one cycle every wait state of the FSM spends. A write needs no
strobe and no wait: each of the four \texttt{ram\_wmask} bits writes its byte lane on the
edge where it is high, so \texttt{SB} and \texttt{SH} leave the rest of the word as it was
\notes{Per-byte write enables}. \texttt{IOBus} masks both strobes off outside RAM space, so
a store to an IO register never also writes the RAM word with the same index \notes{RAM
strobes masked outside RAM space}.

The RAM's contents at configuration are the firmware image, \texttt{rtl/firmware.hex}, read
with \texttt{\$readmemh} when the bitstream is synthesised, so a BRAM-boot program is part
of the bitstream and a new program is a new bitstream. The file is read by bare name,
relative to the working directory of the tool, and a missing file leaves the RAM undefined
with no error: pitfall~\ref{pit:bare-name} \notes{Bare file name in \$readmemh}.

\section{The LED register and the UART}

The IO registers are three addresses in the IO region, and none of them is memory: a store
to one is an action and a load from one is a question.

\paragraph{LEDs.} A store to \texttt{IO\_BASE + 4} sets the LED register to the low byte of
the store data. \texttt{SW} and \texttt{SB} both work, since \texttt{IOBus} ignores the byte
mask. The register drives \texttt{LD0} to \texttt{LD7} directly, clears on reset, and reads
as zero \notes{LED register: reset not gated by the clock enable}.

\paragraph{UART data.} A store to \texttt{IO\_BASE + 8} turns into \texttt{uart\_valid}, a
one-cycle pulse, with the low byte as \texttt{uart\_data}. \texttt{UartTx} drops
\texttt{ready} on the same edge and sends the byte as one start bit, eight data bits LSB
first and one stop bit, each 1736 cycles long: 115\,207~baud, 0.006\,\% above 115\,200. A
byte takes 17\,360 cycles, 86.8~\textmu s. The transmitter has no FIFO and ignores
\texttt{valid} while it sends, so a byte stored too early is lost without a trace
\notes{UART send pulse and the status word (bit 9 convention)}.

\paragraph{UART status.} A load from \texttt{IO\_BASE + 0x10} returns a word that is zero
but for bit~9, which is \texttt{!ready}: the transmitter is busy. It is the only IO address
that answers a read, and bit~9 is a convention between \texttt{IOBus} and the firmware,
held equal by the memory-map lint rule. \texttt{fw/putchar.S} is the whole driver: it
stores the byte, then loads the status word until bit~9 is clear, which is why the demos
run at the pace of the UART.

\section{The flash stall}

A read in flash space is the one access the core waits for. In the cycle of the read
strobe, \texttt{IOBus} passes it to \texttt{SPIFlash} with the word address, and the controller
drops chip select and raises \texttt{mem\_rbusy} at the next edge, and holds both for the
whole SPI transaction. The FSM's two wait states hold while \texttt{mem\_rbusy} is high, and
\texttt{write\_rd} in \texttt{WAIT\_DATA} is gated by it, so a stalled load writes nothing
until its word has arrived \notes{Only flash reads stall the core, read mux}.

The transaction is 64 SPI clocks at a sixth of the system clock, 33.3~MHz: the opcode
\texttt{03h} and the 24-bit byte address on \texttt{spiflash\_mosi}, then 32 data bits on
\texttt{spiflash\_miso}. That is 382 cycles of \texttt{mem\_rbusy}, and the instruction
takes 386 cycles, 1.93~\textmu s, where one fetched from the RAM takes 4. The word arrives
lowest address first, each byte MSB first, as \texttt{13 01 01 80}, and the controller swaps the
bytes into \texttt{0x80010113}, \texttt{addi sp,sp,-2048}, little-endian as the RAM returns
it \notes{Byte order of the received word}. Chip select rises right after the last bit, and
\texttt{mem\_rbusy} with it. In that cycle \texttt{WAIT\_INSTR} latches the word and the
core moves on. The controller's clock and its divider are held while chip select is high,
so the first clock pulse of a transaction is as long as the others \notes{Divider held in
reset while idle (short first pulse)}. There is no cache and no prefetch: every word read
from the flash is a transaction of its own, so code runs from the flash about a hundred
times slower than from the RAM, which is what shapes flash boot in the next chapter.

\label{ch:flash}

Every boundary is forced. An uncompressed 7-series bitstream holds every configuration
frame whatever the design, so it is 11\,443\,728 bytes for any design on this part, and it
starts at offset~0, where the FPGA looks at power-on. The flash erases in 64~KB sectors, so
a region written separately must start on a sector boundary. The window ends at 16~MB
because the controller sends the 24-bit address of the plain \texttt{03h} read, which is
also why bit~24 selects flash space (Section~\ref{sec:memmap}). Flash boot writes only the
code window and never offset~0, so the board keeps booting the bitstream it booted before,
provided the write keeps the flash's Quad Enable bit (pitfall~\ref{pit:quad-enable}). On the
owner's board, a readback of the whole chip after tinyraytracer's image was written differed
from the one taken before only in the image's own bytes.

\section{CCLK and STARTUPE2}
\label{sec:cclk}

Three of the flash's four pins, chip select and the two data lines, are multi-function pins
that configuration releases to the design afterwards, so they are ordinary ports in the
constraints file. The clock is different: CCLK is a dedicated configuration pin, and a
design reaches it only through the \texttt{STARTUPE2} primitive~\cite{ug470}, whose
\texttt{USRCCLKO} input reaches the pin once configuration has ended. \texttt{SOC} wires
\texttt{SPIFlash}'s clock to \texttt{USRCCLKO} and takes \texttt{EOS}, end of startup, back
to \texttt{IOBus}, which passes a flash read to the controller only once \texttt{EOS} is high
\notes{SPI flash CCLK access through STARTUPE2}.

The hand-over is not immediate. Vivado's model of \texttt{STARTUPE2} keeps CCLK high after
end of startup until \texttt{USRCCLKO} has risen twice, so the first transaction after
configuration loses two of its 64 clock edges and the flash misreads its command. In the
simulation behind Figure~\ref{fig:wave-flash} that alone costs the first fetch of
\texttt{fw/start\_spiflash.S}, and it is the most likely reason flash boot needs one press
of the reset button after each load on the board (pitfall~\ref{pit:first-fetch}).

\section{Execute-in-place}
\label{sec:xip}

In flash boot the code is not copied into the RAM: the core fetches each instruction from
the flash, and \texttt{.text} and \texttt{.rodata} stay there. What must be writable cannot,
so \texttt{fw/spiflash.ld} places \texttt{.data} and \texttt{.bss} in the RAM, with the
initial values of \texttt{.data} stored in the flash right after the code, and
\texttt{fw/start\_spiflash.S} prepares the RAM before \texttt{main}: it sets \texttt{gp}
to \texttt{IO\_BASE} and \texttt{sp} to the top of the RAM, zeroes \texttt{.bss}, and
copies the stored values into place.

The same copy moves the hottest code into the RAM. Every \texttt{*}, \texttt{/} and
\texttt{\%} in C is a call into \texttt{libgcc} on RV32I, and every character goes through
\texttt{putchar}, so the linker script puts \texttt{libgcc}'s multiply and divide,
\texttt{fw/putchar.S}, \texttt{fw/print.c} and any function marked \texttt{.fastcode} in
the copied section, and the code in the flash calls them at their RAM addresses. For
mandelbrot's flash build that is 1\,228 bytes copied against 1\,172 left in the flash. The
copy costs a few milliseconds at start-up, and RAM for the rest of the run: what is copied
shares the 6~KB with the data and the stack, and nothing checks that the stack stays clear
of it (pitfall~\ref{pit:stack}).

\paragraph{From C to machine code.} \texttt{make -C fw} compiles each C file with
\texttt{gcc -c} and links the objects, the start-up code and \texttt{libgcc} with
\texttt{ld} into an ELF \notes{The compiler and linker flags, one by one}. The store is the
32-bit word \texttt{\flowStoreWord} at address \texttt{\flowStoreAddr}, an S-type word whose
fields Figure~\ref{fig:isa-formats} decodes. The assembly in the
figure is \texttt{gcc -S}'s output, written for the reader, and \texttt{gcc -c} assembles the
same text from a temporary file, so nothing after the compiler reads it. It shows two things
the linked code no longer does: \texttt{li a5,4194304} is a pseudo-instruction, one
\texttt{lui} for \texttt{IO\_BASE}, and \texttt{\%hi(.LC1)} names a string the linker has
not placed yet, so the \texttt{lui} reads \texttt{0x0} only once the string lands in the
first 2~KB.

\paragraph{The firmware image and the block RAMs.} The firmware image is the ELF's bytes as
text for \texttt{\$readmemh}: \texttt{firmware\_words} writes four words a line, each most
significant digit first, so the store is word~\flowStoreIndex, on
line~\flowStoreHexLine{} \notes{Why the ELF-to-hex conversion exists, endianness}. Synthesis
turns the RAM into two \texttt{\flowBramRef}, each 2K deep and 18 bits wide:
\texttt{\flowBramLow} holds the low 16 bits of every word and \texttt{\flowBramHigh} the
high 16, so the store's word is split between them, \texttt{\flowStoreLow} and
\texttt{\flowStoreHigh}, in \texttt{\flowBramInit}. These \texttt{INIT} values become part
of the bitstream, which is why a new program in BRAM boot needs a new bitstream
\notes{Simulation and hardware after a firmware change}.

\paragraph{The bitstream, JTAG and the board.} \texttt{SOC.bit} begins with a short header,
then \flowBitBytes{} bytes of configuration data, \flowBitFileBytes{} bytes in all, the size
of every bitstream for this part, and the FPGA starts reading at the sync word,
\texttt{0xAA995566}~\cite{ug470}. \texttt{board\_program.tcl} loads it over JTAG in
\flowLoadSeconds{}~s, and the first byte of frame~0 arrives before Vivado has exited: the
FPGA runs the design as soon as configuration ends. The frame takes \flowFrameMs{}~ms, which
Section~\ref{sec:showcase} compares with the simulation.

\paragraph{Flash boot.} The same C source, linked with \texttt{fw/spiflash.ld}, runs from
the flash's code window: its first instruction, \texttt{\flowFlashFirst}, sits at
\texttt{0x01D0\_0000}. \texttt{objcopy -O binary} keeps only the bytes, in memory order, so
the word \texttt{\flowFlashWord} becomes \texttt{\flowFlashBytes}, little-endian.
\texttt{write\_cfgmem} wraps the binary in an MCS file, Intel hex for the flash, and
\texttt{board\_flash.tcl} writes those bytes over JTAG and nothing else. The flash-boot
bitstream is loaded as on the left, and the core fetches each instruction from the flash.
On the board, flash boot ran tinyraytracer (Section~\ref{sec:showcase}), and mandelbrot's flash
build is shown as the same program.

\chapter{Verification}
\label{ch:verif}

The design is checked at three levels: one module against values worked out by hand, the
whole SoC against a recorded trace, and the repository against mechanical rules. A make
target runs each check, and each target, a gate, leaves a log that a commit cites.

\section{The ALU unit bench}

\texttt{sim/ALUBench.v} drives the ports of \texttt{rtl/ALU.v} directly and compares ten
right shifts with results worked out by hand from the RV32I specification~\cite{riscv-isa}:
\texttt{SRL}, \texttt{SRA}, \texttt{SRLI} and \texttt{SRAI} on negative, positive and
most-negative operands, by 0, 4, 9 and~31 places, and with the upper bits of the shift
operand set, which the ALU must ignore. The operand the instruction does not use is set to
\texttt{0xDEADBEEF}, so that a wrong operand choice shows. \texttt{make unit} runs it under
iverilog in seconds, and passes only on its final \texttt{PASS} line.

The bench covers what the golden trace cannot. The trace records what the RTL did when it
was captured, right or wrong: \texttt{SRA} shifted logically when the first trace was
captured, and the trace agreed with it until its frame was compared with the C program
compiled natively (pitfall~\ref{pit:sra}). The bench holds the shifts to the specification,
whatever the trace says, and the rest of the ALU is held by the trace alone.

\section{The golden trace}
\label{sec:golden}

\texttt{sim/bench.v} instantiates \texttt{SOC} in BRAM boot and records only what an
observer outside the chip could see: every byte on the UART line, decoded from the pin as a
receiver decodes it, and every change of the LEDs, with its time. It reads no internal
signal, so the RTL can be restructured freely and the same trace still applies. It writes
one line per event and an \texttt{END} line that says why and when the run stopped:

\begin{center}
  \small
  \begin{tabular}{@{}l@{}}
    \texttt{UART 1b} \\
    \quad\vdots \\
    \texttt{LEDS 1031464038 01} \\
    \texttt{END stop\_leds cycles=206292808 uart\_bytes=11014 leds=01} \\
  \end{tabular}
\end{center}

The run stops when the LED register becomes~1, which the mandelbrot demo writes at the top
of its second frame, so the trace holds exactly one frame: 206\,292\,808 cycles, 1.031~s of
simulated time, 11\,014 UART bytes and one LED change (\texttt{docs/baseline.md}). The
\texttt{END} line carries the cycle count on purpose: a change that keeps every byte but
alters the timing of a single instruction fails, so the trace holds the cycle counts of
Table~\ref{tab:cycles} as well as the results. Two comparisons tie the trace to things
outside the simulation: its UART bytes are, byte for byte, the first frame
\texttt{fw/mandelbrot.c} prints when compiled natively for the PC, and the first frame the
real board sent (Section~\ref{sec:showcase}).

\section{The regression}

\texttt{sim/run\_regression.sh} compiles the files of \texttt{vivado/rtl\_sources.txt} and
the bench in xsim, links the committed firmware image into its build directory, since
\texttt{Memory.v} reads it by bare name (pitfall~\ref{pit:bare-name}), simulates, and
compares the new trace with the golden one. It passes only when the two are byte-identical,
and the full run takes five to six minutes. With \texttt{--max-cycles} it is the smoke run: the
truncated trace must be a prefix of the golden one, which catches most mistakes in
25~seconds. \texttt{make golden} overwrites the golden trace with a new run, and is meant
for an intended change of behaviour only, whose commit says why.

The regression runs one program in one boot mode. Mandelbrot's code holds 24 of the 37
RV32I instructions other than \texttt{FENCE}, \texttt{ECALL} and \texttt{EBREAK}. It never
executes \texttt{SLL}, \texttt{SRA}, \texttt{SLT}, \texttt{SLTU}, \texttt{XOR},
\texttt{SLTI}, \texttt{SLTIU}, \texttt{XORI}, \texttt{ORI}, \texttt{LB}, \texttt{LH},
\texttt{LHU} or \texttt{SH}, and no gate runs them through the core. The flash is not
covered either: the bench has no flash model, and flash boot is simulated only by the
report's own bench for the waveforms of Figure~\ref{fig:wave-flash}.

\section{The gates}

The gates are the targets of the root \texttt{Makefile} (Table~\ref{tab:entry-points}).
Each but \texttt{check}, which only runs its three parts, writes a log in
\texttt{build/logs/} ending in \texttt{PASS} or \texttt{FAIL}, and
\texttt{docs/CONTRIBUTING.md}, ``Gates and evidence'', says which a change needs:
\texttt{make lint} before every commit, \texttt{make smoke} after each RTL edit,
\texttt{make -j2 check} once per change and before any push, and \texttt{make baseline} when
the change must show that timing still holds, since \texttt{make check} stops after synthesis.
A commit message cites the log of each gate it ran. The commit-msg hook refuses a citation
of a log that does not exist or did not pass, and a message that claims a pass without
citing a log. The pre-commit hook runs \texttt{make lint}, and GitHub Actions runs it again
on every push.

\texttt{make lint} holds what no reviewer should have to check by eye. Rule~1 finds tool
by-products beside the sources, which is how a tool run from the wrong directory shows
(pitfall~\ref{pit:bare-name}). Rule~2 finds retired paths and vocabulary, rule~3 limits
Markdown prose to 100 characters a line, rule~4 holds \texttt{vivado/rtl\_sources.txt}
equal to the files in \texttt{rtl/}, and rules 5, 6, 7 and~9 hold the naming and banner
conventions of \texttt{docs/CONTRIBUTING.md}. Two rules hold copies equal to their source:
rule~8 holds every firmware copy of the memory map, and the README's tables, equal to
\texttt{rtl/defines.vh}, and rule~10 holds the trace numbers of \texttt{docs/baseline.md}
equal to the golden trace. Each of the two has a self-test that changes every value the
rule checks and expects it to fail, and lint runs both every time.

\section{Timing}

The one constraint, the 5~ns period of the 200~MHz clock, is met on every one of the
\implEndpoints{} timed endpoints: the worst setup slack (WNS) is \implWNS~ns and the worst
hold slack \implWHS~ns, so the design would close at up to \implFmax~MHz. The worst path
(Figure~\ref{fig:worst-path-schematic}) is the load path.

It starts at \texttt{\implPathStartCell}, an opcode bit of the instruction register, and
ends at the data input of the register file's LUT RAM: the write of \texttt{rd}. Its first
\implPathHead{} LUTs decode the instruction and choose its immediate, a carry chain of
\implPathCarry{} \texttt{CARRY4} adds it to \texttt{rs1}, the load-store address, as far as
bit~24, the bit that selects the flash region, and the last \implPathTail{} LUTs use that
bit to choose the bus's read data, cut out the loaded byte or halfword and pass it to the
write port: \implPathLevels{} levels in all. The address is not registered, so the write in
\texttt{WAIT\_DATA} waits on the whole adder again. Of the path's \implPathDelay~ns,
\implPathLogic~ns are in the cells and \implPathNet~ns, \implPathNetPct\,\%, in the routing
between them. Routing dominates, as it usually does on an FPGA: fewer levels, not faster
cells, would shorten the path, and registering the load-store address, or only its region
bit, would take the adder off it (pitfall~\ref{pit:worst-path}).
Figure~\ref{fig:timing-margin} shows the margin of the rest of the design: most endpoints
have well over a nanosecond to spare, and \implNoLogic{} have no logic at all between their
two ends.

\chapter{For the next student}
\label{ch:next}

This chapter is for whoever extends the design next: the traps this project fell into, and
where to go from here.

\section{Pitfalls}

Each pitfall below cost time once. Each gives the symptom as it showed, the cause, and
where the design or the repository now handles it, and the other chapters cite them by number.

\pitfall{pit:uart-pins}{The UART pin-direction trap}
{Not one byte reaches the PC and the bridge's activity LED never blinks, while the design
looks healthy in simulation.}
{The board's net names mix two points of view: TX and RX are the PC's, \texttt{\_in} and
\texttt{\_out} the FPGA's, so \texttt{uart\_rx\_out} is the FPGA's transmit line. Reading
\texttt{\_in} as ``into the PC'' swaps the two pins. A testbench that prints what the core
handed the UART, instead of decoding the pin, cannot see it.}
{The ports of \texttt{SOC} keep the board's names and directions, which the constraints file
and the testbench bind to, and \texttt{sim/bench.v} decodes the \texttt{uart\_rx\_out} pin as
a receiver does \notes{UART port names and the pin-direction trap}.}

\pitfall{pit:bare-name}{The firmware image read by bare file name}
{In simulation the program does nothing: the LEDs stay at zero and the RAM reads
\texttt{x}, with only a warning in xsim's log. After a Vivado run, \texttt{.Xil/} and
\texttt{clockInfo.txt} appear beside the sources.}
{\texttt{Memory.v} reads \texttt{firmware.hex} with \texttt{\$readmemh} by bare name,
relative to the working directory of whichever tool runs, and a missing file leaves the RAM
undefined without an error.}
{Every script that simulates or synthesises runs in a directory of its own with the image
linked or copied in, and lint rule~1 fails on by-products beside the sources
\notes{Bare file name in \$readmemh}.}

\pitfall{pit:init-values}{The simulation hang without initial values}
{The simulation runs but the flash controller never starts its clock, and the testbench
hangs. The same RTL works on the board.}
{A register with no initial value starts as \texttt{x} in simulation, and
$\texttt{x} + 1$ stays \texttt{x}: the clock divider of \texttt{SPIFlash} never counted.
Configuration loads a definite value into every flip-flop, so the silicon never shows it.}
{\texttt{div} and \texttt{sclk} in \texttt{rtl/SPIFlash.v} declare initial values, and the
core's registers declare their reset values as initial values. A new counter needs one too
\notes{Explicit initial values on div and sclk (simulation hang)}.}

\pitfall{pit:sra}{SRA behaving as SRL}
{The golden trace's frame diverged from the C program compiled natively at row~8, pixel~36:
\texttt{-1544416 >> 9} gave \texttt{0x007FF437} where \texttt{0xFFFFF437} was right.}
{In Verilog an expression's operands decide its signedness together. In
\texttt{funct7[5] ? (\$signed(a) >>> s) : (a >> s)} the unsigned arm makes the whole
conditional unsigned, and \texttt{>>>} then shifts logically.}
{Both arms of the shift in \texttt{rtl/ALU.v} are signed, \texttt{sim/ALUBench.v} checks the
four right shifts on negative operands, and the golden trace was captured again. The sign fill
cost 54 LUTs \notes{SRL versus SRA, as the comment described it}.}

\pitfall{pit:first-fetch}{Flash boot loses its first fetch}
{With the flash-boot bitstream loaded over JTAG, no byte arrives on the UART and the LEDs
stay dark. One press of the CPU RESET button, and the demo runs from then on.}
{Most likely the core's first fetch from the flash is lost straight after configuration.
That fetch is \texttt{lui gp,0x400}, the first instruction of
\texttt{fw/start\_spiflash.S}, which sets \texttt{gp} to \texttt{IO\_BASE}. Without it the
UART writes land in the RAM instead. \texttt{STARTUPE2} passes \texttt{USRCCLKO} to the
CCLK pin only after a few edges, so the first transaction misses clock edges and the flash
misreads its command (Section~\ref{sec:cclk}). And \texttt{IOBus} drops, rather than stalls,
a fetch requested before end of startup. ST\_NICCC shows the same loss in BRAM boot, where
the first flash access is a data read: its first frame came out wrong, while the frames after
it were drawn from the right data (Section~\ref{sec:showcase}).}
{On the board only: press the reset button once after each load. A candidate fix, not kept
in the repository, made the board print straight after the load: \texttt{eos} moves into
\texttt{SPIFlash}, which makes one throwaway read as soon as \texttt{eos} rises and holds a
read requested before that, busy, until it can start it. It cost about 25 LUTs and 25
flip-flops more and met timing with 0.334~ns of slack.}

\pitfall{pit:reset-wait-data}{Reset landing in WAIT\_DATA}
{With the reset state changed to \texttt{FETCH\_INSTR}, the obvious choice, nothing shows
in BRAM boot. In flash boot the first fetch after a press of the reset button goes wrong.}
{\texttt{FETCH\_INSTR} asserts the read strobe for as long as it lasts. Held in reset there,
with \texttt{pc} in flash space, the core would restart the SPI transaction on every cycle,
chip select held low: the flash would see a command it never finishes.}
{\texttt{rtl/Control.v} resets into \texttt{WAIT\_DATA}, which asserts nothing and falls
through to \texttt{FETCH\_INSTR}. Its write-back is harmless, because the instruction
register resets to a no-op whose destination is \texttt{x0} \notes{Reset lands in
WAIT\_DATA, not FETCH\_INSTR}.}

\pitfall{pit:worst-path}{The worst path ends in the register-file write}
{A small change on the load path, one more term in the address decode or in the load lanes,
can miss the 5~ns of the 200~MHz clock: the worst path has \implWNS~ns of slack.}
{The load-store address, \texttt{rs1 + imm}, is not registered, so every cycle of a load
computes it again: \implPathLevels{} levels and \implPathDelay~ns from an opcode bit
through the adder, the region decode and the load lanes into the register file's write
data (Chapter~\ref{ch:results}).}
{Not yet: a comment at \texttt{loadstore\_addr} in \texttt{rtl/Processor.v} marks it.
Register the address in \texttt{EXECUTE}, or only its region bit, and the adder leaves the
path. \texttt{LOAD} and \texttt{STORE} follow \texttt{EXECUTE}, so the register costs no
cycle.}

\pitfall{pit:quad-enable}{Writing the flash clears the Quad Enable bit}
{After a flash write with ``Configuration File Only'', the board no longer boots at
power-on: DONE off, no error flag, the mode pins right, and every byte of the flash intact.}
{Vivado's \texttt{program\_hw\_cfgmem}, with \texttt{PROGRAM.SKIP\_QE\_BIT\_ERASE} at its
default, clears the S25FL256S's non-volatile Quad Enable bit, which the factory bitstream
needs to read the flash four bits wide. A write with an SPIx4 \texttt{.prm} does not set it
back, and Vivado's Tcl has no command that reads the flash's registers~\cite{ug835}.}
{\texttt{docs/design/scripts/board\_flash.tcl write} sets \texttt{SKIP\_QE\_BIT\_ERASE}
to~1, and a write with it kept the bit. \texttt{scripts/flashregs/FlashRegs.v}, loaded over
JTAG, prints the flash's registers on the UART and, built with \texttt{WRITE\_REGS=1},
writes the bit back, which repaired the owner's board (\texttt{figures/README.md}, ``The
Quad Enable bit'').}

\pitfall{pit:stack}{The stack runs into the program}
{A program that has grown wanders off into garbage after a while, or prints nonsense, with
no warning from the build.}
{In BRAM boot the 6~KB of RAM hold the code, the data and the stack, which grows down from
\texttt{0x1800} into the same space. In flash boot it shares the RAM with the copied code.
Nothing checks how deep the stack goes.}
{In part. \texttt{firmware\_words} refuses an image past \texttt{-max\_addr}, which
\texttt{fw/Makefile} sets to the RAM size. Set lower, it reserves room for the stack. The
stack itself is not checked \notes{firmware\_words arguments, -max\_addr as a stack guard}.}

\pitfall{pit:debug-data}{Debug data loaded into the RAM}
{None at run time. The image is larger than its code, though: 852 words, 3\,408 bytes, and
\texttt{objdump -D} shows runs of \texttt{.insn} nonsense after \texttt{\_\_mulsi3} and
\texttt{\_\_modsi3}.}
{\texttt{fw/bram.ld} keeps the catch-all \texttt{*(.*)} of~\cite{levy-learnfpga}, which
places every section of every input file in the RAM, and Ubuntu's \texttt{libgcc.a} carries
DWARF debug sections: 1\,084 bytes, 18\,\% of the 6~KB, never fetched but taken from the
room the stack grows into.}
{Not handled. The committed image is the one this report describes. Adding
\texttt{*(.debug*)} to \texttt{/DISCARD/} gives a 2\,324-byte image \notes{bram.ld line by
line, the /DISCARD/ workaround}.}

\section{Extensions, ranked}

The list is ranked by what each extension gains for the work it takes. None is begun, and each
names where it enters the design.

\begin{enumerate}[leftmargin=*, itemsep=2pt]
  \item \textbf{Pipelining.} A five-stage pipeline retires close to one instruction a cycle,
    a gain of four to six on code bound by computation. It needs a second memory port, which
    the block RAM has, forwarding and a stall after a load, a flush on a taken branch, and a
    stall while \texttt{mem\_rbusy} is high. The stages split the worst path
    (pitfall~\ref{pit:worst-path}). The golden trace's cycle count will change and its bytes
    must not: a new trace with \texttt{make golden}. In flash boot every fetch costs 382
    cycles, so there a small instruction cache gains more than a pipeline.
  \item \textbf{The M extension.} Every \texttt{*}, \texttt{/} and \texttt{\%} in C is a call
    into \texttt{libgcc} today, and mandelbrot multiplies in its inner loop. The device's DSP
    blocks multiply 32 by 32 bits in a few cycles, and a divider fits the FSM as one more
    state that holds like the waits. The firmware then builds with \texttt{-march=rv32im}.
  \item \textbf{UART receive.} \texttt{uart\_tx\_in}, pin Y20, is wired and unused. A receiver
    mirrors \texttt{UartTx}, and a data register and a ready bit take the next IO address
    bit (Section~\ref{sec:memmap}). It allows a serial boot loader: a new program in the RAM
    without a new bitstream or a flash write. Mind the pin names
    (pitfall~\ref{pit:uart-pins}).
  \item \textbf{Interrupts.} They need the control and status registers of Zicsr, at least
    \texttt{mstatus}, \texttt{mtvec}, \texttt{mepc} and \texttt{mcause}. Today their opcode
    stops the core. A timer and the UART receiver are the natural first sources. They touch
    \texttt{Decoder}, \texttt{Control}, which needs a trap state, and the \texttt{pc}
    multiplexer.
  \item \textbf{DDR3.} The board's 1~GB comes through AMD's Memory Interface Generator, with
    a clock domain of its own and a latency of tens of cycles. The bus already waits on
    reads, through \texttt{mem\_rbusy}, but has no way to stall a write, and without a cache
    every access pays the latency.
  \item \textbf{HDMI.} A pixel clock, TMDS encoding through the output serialisers, and a
    frame buffer: 300~KB for 640 by 480 pixels at 8 bits, which fits in the device's block
    RAM but belongs in DDR3, which is why it comes last.
\end{enumerate}

\chapter{Conclusions}
\label{ch:concl}

The project set out to run compiled C on a processor of its own, on a real board, and to
understand every layer in between. It did. A multi-cycle RV32I core of \implLUTs{} LUTs,
with 6~KB of RAM, three IO registers and a flash controller, runs at the Genesys~2's
200~MHz with \implWNS~ns to spare, draws the Mandelbrot set over the UART from the block
RAM, and renders a ray-traced picture in place from the flash.

Three things the results show are worth stating plainly. First, the simulation is a
faithful stand-in for the board: the frame the board sent is byte for byte the golden
trace's, and its time matches the trace's cycle count to a fraction of a percent, so a
change that keeps the trace keeps the hardware's behaviour. Second, the core is not what
limits these demos. The UART is. A byte takes 87~\textmu s and a frame is nearly all bytes,
so a pipelined core or a multiplier would change nothing visible until the output path
changes with it. Third, most of the time lost went to things outside the core: the board's
net names, the working directory a tool runs in, Verilog's signedness rules, the flash
clock's hand-over after configuration, and a bit in the flash's configuration register.
Chapter~\ref{ch:next} records each with its symptom, so that the next student loses hours
where this project lost days.

What is left is also recorded. The first read from the flash after configuration goes
wrong, which in flash boot costs a press of the reset button after each load. The stack is
unguarded, the firmware image carries debug data it never fetches, and thirteen of RV32I's
instructions are executed by no gate. Beyond those, Chapter~\ref{ch:next} ranks the
extensions, pipelining first, and the board has room for all of them.
